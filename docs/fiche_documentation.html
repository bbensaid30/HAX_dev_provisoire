Partie 1 : Commentaires vs Docstrings — Deux Usages Distincts (10 min)

En Python, il existe deux mécanismes pour annoter un programme. Les confondre est l’une des erreurs les plus fréquentes chez les développeurs débutants.

  ┌─────────────────────────────────────────────────────────────────────────┐
  │  COMMENTAIRE (# ...)                  DOCSTRING ("""...""")             │
  │                                                                         │
  │  • Destinataire : le développeur      • Destinataire : l'utilisateur    │
  │    qui lit l'intérieur du code.         qui appelle la fonction/classe. │
  │  • Rôle : explique le « POURQUOI »    • Rôle : définit le CONTRAT       │
  │    d'un choix technique complexe.       d'interface (entrées/sorties).  │
  │  • Ignoré par Python à l'exécution.   • Compilé dans l'attribut __doc__ │
  │                                         et affiché par help() / IDE.    │
  └─────────────────────────────────────────────────────────────────────────┘

1.1 Le Commentaire (#) : Expliquer le « Pourquoi », Jamais le « Quoi »

Un commentaire explique une intention algorithmique, une subtilité mathématique ou un contournement système qui ne se devine pas à la lecture du code.

# MAUVAIS : paraphrase inutilement le code Python
x = x + 1  # Incrémente x de 1

# BON : explique la raison métier ou technique non évidente
# Inversion [lon, lat] -> [lat, lon] requise par Folium (norme GeoJSON RFC 7946)
lat, lon = coords[1], coords[0]

1.2 La Docstring ("""...""") : Le Contrat d’Interface (PEP 257)

Définie par la convention officielle PEP 257, une docstring (documentation string) est une chaîne de caractères entourée de triples guillemets doubles """...""" placée comme toute première instruction d’un module, d’une classe, d’une méthode ou d’une fonction.

Contrairement aux commentaires, Python conserve cette chaîne en mémoire dans l’attribut spécial __doc__ :

  • Taper help(ma_fonction) dans un terminal affiche immédiatement la docstring.
  • Survoler la fonction dans VS Code ou PyCharm affiche la docstring dans une infobulle.
  • Les outils de documentation automatique (Sphinx, MkDocs) extraient ces chaînes pour construire un site web complet.

Règle fondamentale : Typage Statique + Docstring

En Python moderne (\(\ge 3.10\)), les annotations de types (Type Hints) indiquent déjà la nature informatique des variables (n_simulations: int). La docstring ne doit pas se contenter de répéter « entier » : elle doit préciser le sens physique ou métier, les bornes de validité, les unités et la structure exacte des objets retournés.

Partie 2 : Les Standards Professionnels (NumPy & Google) (10 min)

Dans l’écosystème Python scientifique et Data Science, deux formats de docstrings font autorité : le style NumPy (utilisé par NumPy, SciPy, Pandas, scikit-learn) et le style Google (utilisé par Google, TensorFlow, FastAPI).

Règle d’équipe : Choisissez un seul style pour l’ensemble du dépôt PyArena et appliquez-le partout.

2.1 Exemple de Référence : Style NumPy (Recommandé en Calcul Scientifique)

def run_monte_carlo(
    f1: BaseFighter,
    f2: BaseFighter,
    n_simulations: int = 5000,
    n_jobs: int = -1,
    seed: int | None = None,
) -> dict[str, Any]:
    """Estime l'issue d'un duel par simulation de Monte-Carlo multi-cœurs.

    Exécute ``n_simulations`` combats indépendants entre ``f1`` et ``f2``
    en répartissant la charge sur plusieurs processus travailleurs isolés.
    Chaque worker reçoit une graine orthogonale dérivée via ``SeedSequence``.

    Parameters
    ----------
    f1 : BaseFighter
        Premier combattant engagé (statistiques normalisées au niveau 50).
    f2 : BaseFighter
        Second combattant engagé.
    n_simulations : int, default=5000
        Nombre total de duels à simuler. Doit être strictement positif.
    n_jobs : int, default=-1
        Nombre de processus parallèles alloués (``-1`` mobilise tous les
        cœurs physiques disponibles).
    seed : int or None, default=None
        Graine maîtresse garantissant la reproductibilité stricte des tirages.

    Returns
    -------
    dict[str, Any]
        Dictionnaire de synthèse statistique contenant les clés suivantes :
        - ``"winrate"`` (float) : probabilité empirique de victoire de ``f1`` dans [0, 1].
        - ``"ci_95"`` (tuple[float, float]) : intervalle de confiance asymptotique à 95 %.
        - ``"turns_mean"`` (float) : durée moyenne des affrontements (en tours).
        - ``"turns_median"`` (float) : médiane empirique de la durée des combats.
        - ``"turns_std"`` (float) : écart-type corrigé (``ddof=1``) des durées.

    Raises
    ------
    ValueError
        Si ``n_simulations <= 0``.
    """

2.3 Vérification Automatique de la Syntaxe avec ruff

L’outil ruff que vous utilisez déjà dans votre CI/CD intègre les règles pydocstyle (code D) qui auditent automatiquement vos docstrings :

  • Présence d’une docstring sur chaque module, classe et fonction publique.
  • Première ligne rédigée à l’impératif et terminée par un point (.).
  • Présence d’une ligne vide entre le résumé d’une ligne et la description détaillée.

Testez cet audit sur votre code métier via :

ruff check src/ --select D

Partie 3 : Le README.md Reproductible & Les Générateurs Web (10 min)

3.1 Anatomie d’un README.md Professionnel

À la racine de votre dépôt GitHub, le fichier README.md est la vitrine de votre projet. Un correcteur ou un recruteur doit pouvoir installer et lancer votre application en moins de deux minutes sans vous poser de question.

Votre README.md doit impérativement comporter ces 6 sections :

  1. Titre & Présentation : Nom du projet (PyArena), contexte du module M1, présentation de l’extension thématique attribuée (1 à 10) et lien public vers l’application déployée (le cas échéant).

  2. Architecture du Dépôt : Arborescence commentée distinguant src/pyarena/ (moteur métier), app/ (interface multipages Streamlit), tests/ (suite pytest) et data/ (cache et GeoJSON).

  3. Installation Reproductible : Commandes exactes étape par étape :

    git clone <url-du-depot>
cd pyarena
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

  4. Utilisation & Lancement du Dashboard :

    pyarena-app

  5. Tests & Qualité Logicielle : Commandes permettant de rejouer les tests unitaires et de vérifier la couverture :

    pytest --cov=pyarena --cov-report=term-missing
ruff check src/ app/ tests/

  6. Équipe & Contributions : Liste des membres du groupe et répartition des modules développés.

3.2 Comment Génère-t-on la Documentation Web des Bibliothèques ? (Sphinx & MkDocs)

Lorsque vous consultez la documentation officielle en ligne de NumPy, Pandas ou Scikit-Learn, personne n’a écrit ces milliers de pages HTML à la main : elles sont générées automatiquement à partir des docstrings du code source.

Deux outils dominent l’écosystème Python :

  • Sphinx (sphinx-doc.org) : Le standard historique du calcul scientifique. Grâce aux extensions sphinx.ext.autodoc et sphinx.ext.napoleon, Sphinx importe vos modules Python, lit vos docstrings au format NumPy/Google et génère un site HTML ou un manuel PDF LaTeX.
  • MkDocs + mkdocstrings : L’alternative moderne en pur Markdown, très rapide à déployer gratuitement sur GitHub Pages via une action CI.

Pour le rendu de PyArena, il n’est pas exigé de déployer un site Sphinx complet : la priorité absolue est d’avoir des docstrings complètes et homogènes dans src/pyarena/ et un README.md irréprochable.
