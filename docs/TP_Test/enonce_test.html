De l’Arbitrage de Z-Arena aux Suites de Tests Scientifiques & Stochastiques

Auteur·rice

Bensaid Bilel

Date de publication

Objectifs et Démarche Pédagogique

Lors de la séance précédente, nous avons doté nos combattants d’un état protégé (@property) et d’invariants sanctuarisés avec raise. Pour valider notre code, nous écrivions de petits scripts impératifs (test_exo.py) fondés sur des instructions assert exécutées séquentiellement.

Cette approche artisanale présente trois limites fondamentales en ingénierie logicielle :

  • Interruption prématurée : dès qu’une assertion échoue, le script s’arrête net. Il est impossible de savoir si les cinquante assertions suivantes auraient fonctionné.
  • Pollution d’état : si un test modifie les points de vie d’un objet en mémoire, les vérifications suivantes travaillent sur des données altérées (absence d’isolation).
  • Diagnostic opaque : un assert Python standard ne fournit aucun rapport synthétique sur les temps d’exécution, la matrice des cas d’échec ou la couverture de code.

L’objectif de cette séance est d’adopter les standards de la qualité logicielle professionnelle et de l’ingénierie des données :

  1. Comprendre le cycle complet de capture des anomalies via le bloc try / except / else / finally.
  2. Assimiler la théorie du test logiciel (motif AAA, typologie des tests).
  3. Découvrir et maîtriser le cadre de référence en Python : pytest.
  4. Valider méthodiquement les cas nominaux (Happy Path) avant d’éprouver les cas d’erreur (Sad Path) avec pytest.raises.
  5. Factoriser nos environnements de test grâce aux fixtures et aux tests matriciels (@pytest.mark.parametrize).
  6. Tester le code stochastique et les simulations de Monte Carlo sans créer de tests intermittents (flaky tests).
  7. Isoler les accès disque et le cache grâce à la fixture native tmp_path, et catégoriser les calculs lourds avec des marqueurs personnalisés (@pytest.mark.slow).
  8. Mesurer la rigueur de notre travail avec la métrique de couverture de code (code coverage).

Partie 0 : Architecture Projet & Arborescence (15 min)

0.1 Séparation Code Source / Code de Test

Dans un projet Python packagé selon l’architecture src-layout, les fichiers de test ne doivent jamais être mélangés aux fichiers sources de l’application. Ils résident dans un répertoire miroir dédié nommé tests/ placé à la racine du dépôt :

tp-exercices/
├── pyproject.toml            # Configuration du paquet, de Ruff et de Pytest
├── src/                      # CODE DE PRODUCTION (distribué et installé)
│   └── zarena/
│       ├── __init__.py
│       ├── battle.py         # Moteur de duels stochastiques & Monte Carlo
│       ├── exceptions.py     # Classes d'exceptions métier (ZArenaError...)
│       ├── records.py        # Sérialisation et journalisation disque
│       ├── referee.py        # Fonctions d'arbitrage et d'orchestration
│       └── warriors.py       # Modèles (ArenaFighter, BaseWarrior, Saiyan, Cyborg)
└── tests/                    # CODE DE VALIDATION (strictement interne au dépôt)
    ├── __init__.py
    ├── conftest.py           # Fixtures partagées à l'échelle du projet
    ├── test_battle.py        # Tests stochastiques et déterminisme
    ├── test_cyborg.py        # Tests paramétrés du blindage et dunders
    ├── test_records.py       # Tests d'I/O isolés via tmp_path
    ├── test_referee.py       # Tests d'intégration de l'arbitrage
    ├── test_saiyan.py        # Tests unitaires du SaiyanWarrior
    └── test_warriors.py      # Tests unitaires de BaseWarrior
Pourquoi placer tests/ en dehors de src/ ?

Lorsque votre paquet est construit pour être distribué via pip install zarena, seuls les fichiers du répertoire src/ sont assemblés dans l’archive finale (la wheel .whl). Placer tests/ à la racine évite d’alourdir inutilement le paquet distribué avec des dizaines de fichiers de tests, de fixtures et de données d’évaluation.

Partie 1 : Le Cycle de Vie des Exceptions en Python (25 min)

1.1 Lever vs Intercepter : La Philosophie du Traitement d’Erreurs

En programmation défensive :

  • Le composant de bas niveau (la méthode BaseWarrior.take_damage) constate qu’une règle est violée (ex. subir un coup alors que is_alive is False). Son rôle est d’interrompre immédiatement son flux d’instructions et d’émettre une alerte formelle via raise.
  • Le composant de haut niveau (l’arbitre de l’arène ou une boucle de jeu) intercepte cette alerte pour réagir sans faire planter brutalement l’application.

Le mécanisme de capture repose sur quatre blocs complémentaires :

try:
    # 1. Bloc surveillé : code susceptible de lever une exception
    degats = attaquant.execute_attack()
    defenseur.take_damage(degats)
except FighterFaintedError as err:
    # 2. Bloc de secours : exécuté UNIQUEMENT si l'erreur ciblée survient
    print(f"Action refusée par l'arbitre : {err}")
else:
    # 3. Bloc de succès : exécuté UNIQUEMENT si AUCUNE exception n'a été levée
    print(f"Assaut validé : {degats} dégâts appliqués.")
finally:
    # 4. Bloc de clôture : exécuté SYSTÉMATIQUEMENT, quoi qu'il arrive
    reinitialiser_chrono_tour()

1.2 Le Polymorphisme Appliqué aux Exceptions

Dans notre module src/zarena/exceptions.py, nous disposons de la hiérarchie suivante :

\[\text{Exception} \longrightarrow \text{ZArenaError} \longrightarrow \begin{cases} \text{InvalidStatError} \\ \text{FighterFaintedError} \\ \text{NotEnoughKiError} \end{cases}\]

Puisque FighterFaintedError hérite de ZArenaError, une clause d’interception sur la classe parente intercepte automatiquement toutes ses classes filles :

try:
    cible.take_damage(50)
except ZArenaError as err:
    # Intercepte indifféremment FighterFaintedError ou InvalidStatError
    journaliser_incident(err)
Règle d’or : L’Ordre d’Évaluation des Blocs except

Python évalue les clauses except séquentiellement de haut en bas et s’arrête au premier bloc compatible. Vous devez toujours capturer les exceptions les plus spécifiques en premier et les classes parentes génériques en dernier :

try:
    guerrier.blast_attack()
except NotEnoughKiError:
    # 1. Cas très spécifique : manque de ressource tactique
    guerrier.recharge_ki(20)
except ZArenaError:
    # 2. Cas général : tout autre incident du moteur Z-Arena
    annuler_tour()

1.3 Exercice 1 : L’Arbitre Sécurisé de l’Arène [Guidage Moyen]

Dans un fichier src/zarena/referee.py, nous souhaitons concevoir une fonction d’arbitrage sécurisée qui tente d’exécuter un échange de coups entre deux entités sans laisser planter le simulateur.

Cahier des charges

Implémentez la fonction safe_attack_round(attacker: ArenaFighter, defender: ArenaFighter) -> str :

  1. Dans un bloc try, appelle damage = attacker.execute_attack() puis defender.take_damage(damage).
  2. Si defender lève FighterFaintedError, interceptez-la et renvoyez la chaîne exacte : "Coup impossible : défenseur déjà hors combat."
  3. Si une exception InvalidStatError survient (ex. calcul de dégâts illégal), interceptez-la et renvoyez : "Anomalie de combat : statistiques invalides."
  4. Si aucune exception n’est levée (bloc else), renvoyez : f"Assaut réussi : {damage} dégâts infligés."

Transition : Notre code métier sait émettre et gérer des erreurs. Comment vérifier de façon automatisée, reproductible et exhaustive que l’ensemble de ces règles fonctionne sans faille ? C’est le rôle des tests logiciels.

Partie 2 : Théorie du Test & Premiers Tests Unitaires avec pytest (35 min)

2.1 Qu’est-ce qu’un Test Automatisé ? Le Motif AAA

Un test logiciel est un programme déterministe qui exécute une portion de code et compare le résultat obtenu au résultat théorique attendu.

Tout test unitaire propre s’articule autour du motif universel AAA (Arrange - Act - Assert) :

  1. Arrange (Préparer) : instancier les objets nécessaires, initialiser les variables et configurer l’état initial.
  2. Act (Agir) : déclencher l’action ou appeler la méthode cible dont on souhaite tester le comportement.
  3. Assert (Vérifier) : vérifier que l’état résultant ou la valeur retournée est strictement conforme aux spécifications.

2.2 La Typologie des Tests : Des Unités au Système

Dans une base de code, tous les tests n’ont pas la même granularité :

       ▲        / \
       │       /   \      Tests Bout-en-bout (E2E) : Simulation d'un tournoi complet
       │      /-----\
  Coût │     /       \    Tests d'Intégration : safe_attack_round(goku, c17)
       │    /---------\
       │   /           \  Tests Unitaires : BaseWarrior.take_damage(30)
       ▼  /-------------\
          Vitesse d'exécution
  • Tests Unitaires (Unit Tests) : testent le comportement d’un composant élémentaire (une méthode, une fonction) isolé du reste du système. Ils s’exécutent souvent en quelques millisecondes. Exemple : vérifier que krilin.take_damage(30) réduit bien ses PV de 100 à 70.
  • Tests d’Intégration (Integration Tests) : vérifient l’interaction et la communication entre deux ou plusieurs composants distincts. Exemple : vérifier que la fonction safe_attack_round coordonne correctement l’attaque d’un SaiyanWarrior avec la défense d’un Cyborg.
  • Tests de Bout-en-bout (End-to-End / System) : simulent l’application complète depuis l’ingestion des paramètres d’entrée jusqu’à la production du bilan final.

Bien que la frontière entre unitaire et intégration soit parfois subtile en POO, l’intention architecturale reste directrice : valider chaque brique unitairement avant de tester leur assemblage.

2.3 Pourquoi pytest ? La Disséction d’Assertions

Contrairement à l’ancien module standard unittest hérité de Java (qui imposait d’écrire des classes dérivant de TestCase et des méthodes verbeuses comme self.assertEqual), pytest repose sur des fonctions Python simples et l’instruction native assert.

La force de la réécriture d’AST

Quand vous lancez un script Python avec un assert défaillant, vous obtenez un simple AssertionError.

pytest, lui, intercepte l’arbre syntaxique abstrait (AST) avant exécution. En cas d’échec, il affiche une dissection des opérandes :

>       assert krilin.hp == 80
E       AssertionError: assert 70 == 80
E        +  where 70 = <BaseWarrior Krilin>.hp

On visualise immédiatement quelle valeur a été calculée et pourquoi elle diverge de l’attendu.

2.4 Le Cas Nominal (Happy Path) : Premiers Tests sur BaseWarrior

On commence toujours par vérifier le cas où tout se déroule normalement (Happy Path) avant de chercher les cas d’erreur.

Créez le fichier tests/test_warriors.py :

# tests/test_warriors.py
from zarena.warriors import BaseWarrior


def test_base_warrior_creation_nominal() -> None:
    # 1. Arrange & Act
    krilin = BaseWarrior(name="Krilin", hp=100, ki=50, attack_power=30)

    # 3. Assert
    assert krilin.name == "Krilin"
    assert krilin.hp == 100
    assert krilin.max_hp == 100
    assert krilin.ki == 50
    assert krilin.attack_power == 30
    assert krilin.is_alive is True
    assert krilin.is_defeated is False


def test_base_warrior_take_damage_nominal() -> None:
    # 1. Arrange
    warrior = BaseWarrior(name="Krilin", hp=100, ki=50, attack_power=30)

    # 2. Act
    warrior.take_damage(35)

    # 3. Assert
    assert warrior.hp == 65

Partie 3 : Tester les Anomalies avec pytest.raises (30 min)

3.1 Le Cas d’Erreur (Sad Path) : Pourquoi et Comment le Tester ?

Un logiciel robuste ne se contente pas de fonctionner avec des données valides : il doit refuser d’opérer lorsque les données violent ses invariants.

Comment tester qu’une méthode refuse une action et lève bien l’exception attendue ?

Si nous utilisions un bloc try / except manuel, le code de test deviendrait lourd et verbeux. pytest fournit un gestionnaire de contexte dédié : pytest.raises.

import pytest
from zarena.exceptions import InvalidStatError
from zarena.warriors import BaseWarrior


def test_base_warrior_rejects_negative_hp() -> None:
    # On affirme que le bloc ci-dessous DOIT lever InvalidStatError
    with pytest.raises(InvalidStatError) as exc_info:
        BaseWarrior(name="Goku", hp=-50, ki=50, attack_power=30)

    # Vérification optionnelle mais recommandée du message associé
    assert "Statistiques initiales invalides" in str(exc_info.value)

Mécanique de pytest.raises :

  • Si le code à l’intérieur du bloc with lève effectivement l’exception spécifiée, le test réussit.
  • Si le code s’exécute sans lever d’erreur, le test échoue avec le message : Failed: DID NOT RAISE <class 'InvalidStatError'>.
  • Si le code lève une autre exception inattendue (ex. TypeError), le test échoue en affichant la trace d’erreur.

Partie 4 : Isolation d’État : Les Fixtures Pytest & conftest.py (35 min)

4.1 Pourquoi les Fixtures ?

En test logiciel, l’étape de préparation des objets s’appelle le Setup (Arrange).

Si dix tests distincts manipulent un SaiyanWarrior, copier-coller sa création dans chaque fonction entraîne deux problèmes :

  1. Maintenance lourde : si la signature du constructeur évolue, dix fonctions doivent être mises à jour.
  2. Risque de pollution d’état : si les fonctions se partageaient une variable globale VEGETA, le premier test qui lui inflige des dégâts fausserait les assertions des tests suivants.

Une Fixture (@pytest.fixture) est une fonction décorée qui fabrique et fournit un objet prêt à l’emploi à chaque test qui en fait la demande en déclarant son nom en paramètre :

import pytest
from zarena.warriors import BaseWarrior


@pytest.fixture
def fresh_krilin() -> BaseWarrior:
    """Fournit une instance neuve de Krilin à chaque appel de test."""
    return BaseWarrior(name="Krilin", hp=100, ki=50, attack_power=30)


def test_attaque_krilin(fresh_krilin: BaseWarrior) -> None:
    # fresh_krilin est injecté automatiquement par pytest
    assert fresh_krilin.compute_damage() == 30

Par défaut, les fixtures ont une portée dite scope="function" : pytest réexécute la fixture avant chaque fonction de test, garantissant que chaque test travaille sur une instance indépendante.

4.2 Centralisation dans tests/conftest.py

Lorsqu’une fixture doit être partagée entre plusieurs fichiers de test de votre projet, Python permet de la déclarer dans un fichier spécial nommé tests/conftest.py.

Pytest inspecte automatiquement ce fichier : toutes les fixtures déclarées dans conftest.py deviennent immédiatement utilisables dans n’importe quel fichier test_*.py sans aucun import.

Partie 6 : Tester le Hasard & les Simulations Stochastiques (30 min)

6.1 Le Danger des Tests Intermittents (Flaky Tests)

Si un test unitaire exécute un tirage aléatoire sans contrôle :

def test_combat_aleatoire() -> None:
    vainqueur = simuler_match_aleatoire(goku, vegeta)
    assert vainqueur.name == "Goku"  # Echoue 1 fois sur 2 !

Un test qui réussit ou échoue sans que le code source n’ait changé s’appelle un test intermittent (flaky test). C’est le fléau des chaînes d’intégration continue : il paralyse les déploiements et détruit la confiance des équipes dans les tests automatisés.

Pour tester du code stochastique, on applique trois techniques d’ingénierie logicielle :

  1. Rendre l’aléa déterministe via la graine (seed) : pour valider la logique pas à pas.
  2. Tester les invariants mathématiques structurels (Property-Based) : vrais quel que soit le tirage.
  3. Asserts statistiques tolérants (pytest.approx) : pour vérifier la loi des grands nombres.

6.2 Implémentation du Moteur Stochastique (src/zarena/battle.py)

Créez le fichier src/zarena/battle.py. Nous y implémentons un moteur de duel au tour par tour où les attaques physiques oscillent avec une amplitude uniforme de \(\pm 15\%\) (\(U \sim \mathcal{U}[0{,}85 \,;\, 1{,}15]\)) :

# src/zarena/battle.py
from dataclasses import dataclass
from typing import Callable
import numpy as np
from zarena.warriors import ArenaFighter


@dataclass(frozen=True)
class DuelResult:
    """Synthese immuable d'un affrontement dans Z-Arena."""

    winner: ArenaFighter
    loser: ArenaFighter
    turns: int
    remaining_hp: int


def simulate_duel(
    f1: ArenaFighter,
    f2: ArenaFighter,
    seed: int | None = None,
) -> DuelResult:
    """Simule un duel stochastique tour par tour jusqu'au K.-O."""
    rng = np.random.default_rng(seed)
    turns = 0

    while not f1.is_defeated and not f2.is_defeated:
        turns += 1

        # 1. Attaque de f1 avec facteur d'alea physique U ~ [0.85, 1.15]
        u1 = rng.uniform(0.85, 1.15)
        degats_f1 = int(f1.execute_attack() * u1)
        f2.take_damage(degats_f1)

        if f2.is_defeated:
            break

        # 2. Riposte de f2 avec facteur d'alea
        u2 = rng.uniform(0.85, 1.15)
        degats_f2 = int(f2.execute_attack() * u2)
        f1.take_damage(degats_f2)

    winner = f1 if not f1.is_defeated else f2
    loser = f2 if winner == f1 else f1

    return DuelResult(
        winner=winner,
        loser=loser,
        turns=turns,
        remaining_hp=winner.hp,
    )


def run_monte_carlo(
    f1_factory: Callable[[], ArenaFighter],
    f2_factory: Callable[[], ArenaFighter],
    n_simulations: int = 1000,
    seed: int | None = None,
) -> dict[str, float]:
    """Estime le winrate de f1 par simulations de Monte Carlo."""
    rng = np.random.default_rng(seed)
    f1_wins = 0
    total_turns = 0

    for _ in range(n_simulations):
        # On fabrique des combattants frais pour chaque iteration
        f1 = f1_factory()
        f2 = f2_factory()
        # On derive une graine unique par duel pour isoler le tirage
        duel_seed = int(rng.integers(0, 1_000_000))
        result = simulate_duel(f1, f2, seed=duel_seed)

        if result.winner.name == f1.name:
            f1_wins += 1
        total_turns += result.turns

    winrate = f1_wins / n_simulations
    return {
        "winrate": winrate,
        "turns_mean": total_turns / n_simulations,
    }
Focus 1 : Qu’est-ce qu’une @dataclass(frozen=True) ?

Jusqu’à présent, pour créer un objet, nous écrivions systématiquement __init__, self.x = x, puis __repr__ et __eq__. Lorsque l’unique but d’une classe est de stocker des données sans logique métier complexe (un simple enregistrement ou record), ce code est verbeux et répétitif.

Le décorateur @dataclass (module standard dataclasses) génère automatiquement pour vous le constructeur __init__, l’affichage __repr__ et l’égalité __eq__ à partir de vos annotations de type.

L’argument frozen=True verrouille l’objet :

  • Immuabilité stricte : une fois l’instance DuelResult créée à la fin du match, toute tentative d’altération (result.turns = 10) lève immédiatement une exception FrozenInstanceError.
  • Sanctuarisation de l’historique : le bilan d’un combat est une archive figée dans le temps qui ne doit jamais pouvoir être falsifiée a posteriori. C’est exactement ce que requiert le cahier des charges de BattleResult dans le projet PyArena.
Focus 2 : Le typage Callable et le patron de Fabrique (Factory Pattern)

Dans la fonction run_monte_carlo, observez le typage du paramètre :

f1_factory: Callable[[], ArenaFighter].

  • Le type Callable[[Args], Retour] : issu du module typing, il indique que le paramètre attendu n’est pas un objet statique, mais une fonction exécutable. Ici, Callable[[], ArenaFighter] désigne une fonction qui ne prend aucun argument ([]) et qui renvoie un nouveau combattant (ArenaFighter).
  • Pourquoi ne pas passer directement f1: ArenaFighter ? C’est le piège numéro un en simulation multi-agents : si vous passez l’objet goku directement dans la boucle de simulation, il subit des dégâts dès le tour 1 et termine le premier match K.-O. Au duel numéro 2, vous réutiliseriez le même combattant avec 0 PV !
  • La solution : la Fabrique (Factory) : au lieu de transmettre un guerrier déjà blessé, on transmet la « recette » pour fabriquer un guerrier neuf à chaque itération de la boucle de Monte Carlo via l’appel f1 = f1_factory().

Bonne pratique NumPy moderne : default_rng

Ne faites pas appel à l’ancien module global np.random.seed(42). Il modifie l’état global du processus Python et contamine silencieusement les autres tests. Utilisez exclusivement un générateur d’échantillons local et isolé : rng = np.random.default_rng(seed).

# src/zarena/records.py
import json
from pathlib import Path
from zarena.battle import DuelResult


def export_duel_summary(result: DuelResult, filepath: Path | str) -> None:
    """Sauvegarde le bilan d'un affrontement dans un fichier JSON."""
    data = {
        "winner": result.winner.name,
        "loser": result.loser.name,
        "turns": result.turns,
        "remaining_hp": result.remaining_hp,
    }
    path = Path(filepath)
    path.parent.mkdir(parents=True, exist_ok=True)
    with open(path, "w", encoding="utf-8") as f:
        json.dump(data, f, indent=2)

Partie 8 : Couverture de Code (pytest-cov) & Branches Mortes (15 min)

8.1 Qu’est-ce que le Code Coverage ?

La couverture de code (code coverage) mesure le pourcentage d’instructions de votre code source exécutées lors du lancement de votre suite de tests :

\[\text{Couverture} = \frac{\text{Lignes de code exécutées par la suite de tests}}{\text{Nombre total de lignes de code exécutables}} \times 100\]

Dans l’industrie logicielle comme dans les projets académiques, un seuil minimal de couverture (typiquement \(\ge 85\%\)) est exigé pour valider l’intégration d’une fonctionnalité dans la branche principale.

8.2 Générer le Rapport de Couverture

Exécutez pytest en demandant l’analyse de couverture du paquet zarena avec localisation des lignes non testées :

pytest --cov=zarena --cov-report=term-missing
#ou
pytest --cov=src/zarena --cov-report=term-missing # pour la totalité du dossier

Structure du rapport terminal :

  • Stmts : nombre total d’instructions exécutables dans le module.
  • Miss : nombre d’instructions qui n’ont jamais été exécutées par aucun test.
  • Cover : pourcentage d’instructions couvertes.
  • Missing : numéros précis des lignes non traversées (ex. 78-82).

Si une ligne apparaît dans la colonne Missing (par exemple, la méthode recharge_ki de BaseWarrior ou le cas InvalidStatError de safe_attack_round), cela signifie qu’un bug pourrait s’y cacher sans qu’aucun test ne donne l’alerte !
