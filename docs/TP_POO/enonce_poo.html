Cours-TP : Programmation Orientée Objet & Conception Logicielle Robuste

Du Simulateur de Combat Z-Arena aux Principes Généraux de la POO (3h00)

Auteur·rice

Bensaid Bilel

Date de publication

2 octobre 2026

Objectifs et Démarche Pédagogique

Dans les cursus scientifiques, la programmation est souvent abordée sous un angle purement procédural : un script séquentiel manipulant des tableaux NumPy ou des dictionnaires ouverts ({"id": 1, "energie": 100, "statut": "actif"}) transmis à des fonctions isolées.

Si ce style convient à de courts scripts d’exploration numérique ou d’analyse séquentielle, il montre immédiatement ses limites dès que l’on modélise un système complexe, distribué ou composé d’entités autonomes en interaction :

  • Données sans géométrie garantie : un dictionnaire ou un tuple peut recevoir n’importe quelle clé erronée ou omettre un champ sans avertissement de l’interpréteur (KeyError différé ou faute de frappe indétectable par les outils statiques).
  • Absence de protection des invariants : rien n’interdit d’assigner une valeur aberrante (une énergie négative, une masse nulle ou une probabilité supérieure à 1), corrompant silencieusement l’état du système.
  • Dispersion du code : les données d’une entité voyagent à nu entre des fonctions libres sans couplage formel. Aucune fonction n’est explicitement responsable de la cohérence interne de l’objet.

La Programmation Orientée Objet (POO) répond à cette exigence d’ingénierie logicielle : elle permet de lier indissociablement un état interne protégé aux algorithmes qui le manipulent, tout en formalisant des contrats d’interface stricts.

1. Le Fil Rouge du Semestre : Le Simulateur « Z-Arena »

Pour donner un cadre concret et rigoureux à ces problématiques tout au long du semestre, l’ensemble de nos travaux s’articule autour de la construction d’un moteur de combat multi-agents : Z-Arena (inspiré de l’univers de Dragon Ball Z).

Ce choix thématique s’inscrit dans l’histoire de la discipline : la POO a été inventée précisément pour la simulation d’événements discrets et de mondes virtuels peuplés d’agents autonomes (notamment avec les langages Simula 67 puis Smalltalk). L’arène de combat en matérialise naturellement chaque enjeu :

  • Des agents autonomes : chaque combattant (Goku, Vegeta, Piccolo, C-17) possède un état interne propre (points de vie, réserve d’énergie vitale dite Ki, statut de transformation).
  • Des invariants stricts : un guerrier inconscient (0 PV) ne peut plus agir ni subir d’assauts, et l’utilisation de techniques spéciales dépend de ressources finies.
  • Des interactions hétérogènes : l’arène doit orchestrer des affrontements entre des entités aux physiologies dissemblables (un Terrien standard, un Saiyan dont la puissance offensive décuple lors des crises, un Cyborg qui absorbe les chocs) sans que la boucle de jeu n’ait à connaître les détails internes de chaque personnage.

Aborder ce simulateur de façon procédurale exigerait d’éparpiller des dictionnaires et de multiplier les branchements conditionnels (if guerrier["race"] == "saiyan": ...), rendant le code fragile et impossible à faire évoluer.

2. Un Paradigme Universel Dépassant le Cadre Ludique

L’aspect ludique de l’arène n’est qu’un vecteur d’apprentissage. Les mécanismes architecturaux conçus dans ce module sont rigoureusement identiques à ceux utilisés dans l’industrie et la recherche scientifique :

  • En calcul scientifique & physique numérique : une classe Particle ou MeshNode encapsule des coordonnées spatiales, une masse et une vitesse, avec l’invariant physique strict \(m > 0\).
  • En apprentissage automatique & optimisation : dans des bibliothèques industrielles comme PyTorch, nn.Module est une classe dont héritent tous les réseaux de neurones. Elle encapsule des tenseurs de poids (l’état interne protégé) et impose une interface contractuelle commune (forward()).
  • En ingénierie logicielle & finance : un composant OrderBook ou Portfolio doit sanctuariser ses transactions contre les états corrompus et exposer des comportements similaires/polymorphes pour différents types d’actifs financiers.

Apprendre à concevoir l’architecture de Z-Arena, c’est acquérir les réflexes de conception requis pour n’importe quelle bibliothèque logicielle de haut niveau.

Partie 1 : Typage Statique & Analyse de Code (Ruff) : Le Contrat Procédural (25 min)

1.1 Motivation : La Signature d’une Fonction comme Premier Contrat

Avant même d’aborder les objets, considérons une fonction procédurale classique de calcul d’assaut dans notre moteur de simulation :

def calculer_degats(attaque, defense, multiplicateur):
    return (attaque * multiplicateur) - defense

En lisant ce code brut, les ambiguïtés sont immédiates :

  • Quels types attend cette fonction ? Des entiers (int), des flottants (float), ou des tableaux de caractéristiques ?
  • Que se passe-t-il si un utilisateur passe multiplicateur = "x2" au lieu de 2.0 ? Le calcul échoue en plein milieu de la simulation avec un TypeError tardif.
  • Quelle est la nature de la valeur renvoyée ?

En ingénierie logicielle, la signature d’une fonction constitue un contrat formel. Typer ses paramètres permet d’expliciter le comportement attendu et d’autoriser les outils d’analyse statique à repérer les bugs en amont de l’exécution.

1.2 La Syntaxe Moderne du Typage (PEP 484 & PEP 604)

Depuis Python 3.10, la syntaxe des annotations de type (type hints) est unifiée :

  • Types scalaires : nom: str, puissance: int, facteur: float, est_actif: bool.
  • Valeur par défaut :
def calculer_puissance(base: int, bonus: int = 0) -> int:
  • Absence de retour : -> None indique explicitement que la fonction agit par effet de bord (par exemple, logger une information ou écrire dans un fichier) et ne renvoie aucune valeur.
  • Union de types moderne (PEP 604) : La barre verticale | remplace l’ancienne notation verbeuse Union ou Optional :
statut_altere: str | None = None
energie: int | float = 100
  • Conteneurs standards : scores: list[int], registre: dict[str, float].

1.3 Le Rôle du Linter Statique : Ruff

Python est un langage interprété : une faute de frappe sur un nom de variable située dans une branche conditionnelle rare (if coup_critique: ...) peut rester invisible pendant des semaines jusqu’à ce que la condition se réalise et interrompe brutalement le programme.

Dans les langages compilés (C++, Rust), le compilateur intercepte ces anomalies avant la génération du binaire. En Python, c’est le rôle du linter statique.

Ruff est l’outil standard actuel :

  1. Il parcourt l’arbre syntaxique abstrait (AST) de vos fichiers sans exécuter le code.
  2. Il détecte immédiatement les variables non initialisées, les fautes d’inattention, les imports oubliés ou inutiles, et les incohérences de formatage.
  3. Il s’exécute quasi instantanément dans votre terminal : ruff check src/.

1.4 Exercice 1 : Audit Statique d’un Module Procédural (10 min)

Créez un fichier temporaire src/zarena/test_syntaxe.py contenant volontairement des erreurs procédurales :

# src/zarena/test_syntaxe.py
import math  # Module importé mais jamais sollicité


def simuler_attaque(puissance: int, defense: int, bonus: float = 1.0) -> int:
    degats_bruts = int(puissance * bonus) - defense
    return degats_brut  # Faute de frappe sur le nom de la variable locale !

Lancez l’audit statique avec Ruff :

ruff check src/zarena/test_syntaxe.py

Ruff signale immédiatement les deux anomalies sans exécuter la fonction :

  • F401: math imported but unused.
  • F821: Undefined name degats_brut (interception de la faute de frappe).

Supprimez ce fichier de test avant de poursuivre :

rm src/zarena/test_syntaxe.py

Partie 2 : Modéliser l’État et le Comportement — Attributs, Constructeur, Méthodes & Invariants (35 min)

2.1 Classe vs Instance : Le Plan et la Matière

En programmation procédurale, une entité est un simple agrégat passif de variables. En POO, on structure le système en deux niveaux d’abstraction :

  • La Classe (BaseWarrior) : C’est le plan d’architecte (le moule industriel). Elle ne stocke aucune donnée de jeu individuelle : elle formalise la structure que posséderont tous les guerriers (leurs variables, appelées attributs) et les actions qu’ils pourront accomplir (leurs fonctions internes, appelées méthodes).
  • L’Instance (goku, vegeta) : C’est l’objet concret alloué en mémoire issu de ce plan. À partir d’une unique classe BaseWarrior, on peut instancier des dizaines de guerriers indépendants : chacun possède son propre espace mémoire et ses propres valeurs (Goku possède 100 PV et 80 de Ki, alors que Vegeta possède 40 PV et 100 de Ki).

2.2 Les Attributs d’Instance : Donner un État à l’Objet

Un attribut d’instance est une variable rattachée directement à un objet spécifique. Si goku est une instance de guerrier, ses attributs fondamentaux sont son nom ("Goku"), ses points de vie (100), son énergie vitale (50) et sa puissance physique de base (40). On y accède par la notation pointée : goku.name, goku.hp.

Mais comment ces variables sont-elles créées et stockées dès la naissance de l’objet ? C’est le rôle du constructeur.

2.3 Le Constructeur __init__ : Initialiser la Mémoire

Lorsqu’on crée un nouveau guerrier via l’instruction goku = BaseWarrior("Goku", 100, 50, 40), Python déclenche automatiquement une routine d’initialisation appelée le constructeur, matérialisée par la méthode spéciale prédéfinie __init__ (pour initialization, encadrée par deux doubles tirets bas) :

  1. Python alloue d’abord un bloc de mémoire libre pour l’objet (par exemple à l’adresse hexadécimale 0x7f8a10).
  2. Il appelle immédiatement BaseWarrior.__init__(...) en lui transmettant l’adresse de ce nouvel objet comme tout premier paramètre, suivi des arguments fournis ("Goku", 100, 50, 40).
  3. Dans la fonction, ce premier paramètre désignant l’objet en cours de fabrication est conventionnellement et obligatoirement nommé self.
  4. Écrire self.name = name signifie littéralement : « Dans le bloc mémoire désigné par self, enregistre l’attribut name avec la valeur passée en argument ».
class BaseWarrior:
    """Plan de conception d'un guerrier standard dans Z-Arena."""

    def __init__(
        self, name: str, hp: int, ki: int = 50, attack_power: int = 30
    ) -> None:
        # Création et initialisation des attributs d'instance
        self.name: str = name
        self.hp: int = hp
        self.ki: int = ki
        self.attack_power: int = attack_power

Attention au piège classique de portée : Si vous écrivez hp = hp au lieu de self.hp = hp, vous stockez la valeur dans une simple variable locale à la fonction __init__. Dès la fin du constructeur, cette variable locale est détruite de la pile d’exécution. L’instance créée ne stockera aucun attribut hp, provoquant un AttributeError lors du premier appel à une méthode ultérieure.

2.4 Les Méthodes : Donner un Comportement à l’Objet

Maintenant que notre guerrier possède un état (des attributs), nous voulons lui donner des comportements : afficher sa fiche, subir des dégâts ou calculer sa frappe.

Une méthode est une fonction déclarée à l’intérieur d’une classe, conçue spécifiquement pour interagir avec les attributs de l’objet qui l’appelle. C’est ici que self prend tout son sens :

class BaseWarrior:

    def __init__(
        self, name: str, hp: int, ki: int = 50, attack_power: int = 30
    ) -> None:
        self.name: str = name
        self.hp: int = hp
        self.ki: int = ki
        self.attack_power: int = attack_power

    def display_status(self) -> None:
        """Méthode affichant l'état interne du guerrier."""
        print(
            f"Guerrier : {self.name} | Santé : {self.hp} PV | Ki : {self.ki}"
        )

Quand vous écrivez dans votre programme :

goku = BaseWarrior("Goku", 100, 50, 40)
goku.display_status()

L’interpréteur Python traduit automatiquement cet appel en :

BaseWarrior.display_status(goku)  # goku est injecté dans le paramètre self !

Dans le corps de la méthode, self.hp permet donc d’aller lire ou modifier les points de vie de l’instance précise qui a invoqué l’action.

2.5 Mémoire Propre vs Mémoire Partagée : Attributs d’Instance vs Attributs de Classe

Dans un moteur de simulation, certaines variables caractérisent un individu précis, tandis que d’autres appartiennent aux lois de l’univers ou au concept global de l’espèce :

  • Attribut d’instance : déclaré dans __init__ via self.x = .... Chaque objet possède sa propre valeur (Goku et Vegeta ont chacun leur propre self.hp et self.ki).
  • Attribut de classe : déclaré directement dans le corps de la classe, en dehors de toute méthode. Il n’existe qu’en un seul exemplaire en mémoire, partagé par toutes les instances.
class BaseWarrior:
    # ATTRIBUTS DE CLASSE (partagés par l'ensemble des combattants du jeu)
    ARENA_NAME: str = "Championnat du Monde des Arts Martiaux"
    MAX_UNIVERSAL_KI: int = 100
    warriors_count: int = 0

    def __init__(
        self, name: str, hp: int, ki: int = 50, attack_power: int = 30
    ) -> None:
        # ATTRIBUTS D'INSTANCE (propres à ce guerrier précis)
        self.name: str = name
        self.hp: int = hp
        self.ki: int = ki
        self.attack_power: int = attack_power

        # Incrémentation du compteur global via le nom de la classe
        BaseWarrior.warriors_count += 1

Le piège du masquage (shadowing)

Si un développeur écrit goku.ARENA_NAME = "Planète Namek" :

  • Python ne modifie pas l’attribut de classe partagé.
  • Il crée un nouvel attribut d’instance nommé ARENA_NAME sur goku, qui vient masquer localement l’attribut de classe. Les autres guerriers restent rattachés au Championnat du Monde.
  • Règle d’or : Pour lire ou modifier une variable globale de classe, préfixez-la systématiquement par le nom de la classe : BaseWarrior.ARENA_NAME = ....

2.6 Sanctuariser les Invariants: Le Principe Fail-Fast

En conception logicielle, un invariant est une condition logique ou physique qui doit demeurer strictement vraie tout au long du cycle de vie d’un objet.

Dans notre moteur :

  • Les points de vie et le Ki maximals d’un combattant doivent être positifs.
  • Les dégâts subis ne peuvent pas être négatifs (\(\text{damage} \ge 0\)).
  • Une cible déjà K.-O. ne peut plus subir d’assaut.

Plutôt que d’accepter des valeurs incohérentes qui corrompraient silencieusement les calculs de l’arène, un code robuste applique le principe du Fail-Fast : on bloque immédiatement l’exécution en levant une exception standard de Python via le mot-clé raise :

  • ValueError : lorsqu’un argument numérique viole le domaine de définition valide (ex. des PV négatifs ou nuls).
  • RuntimeError : lorsqu’une action est impossible compte tenu de l’état actuel de l’objet (ex. attaquer un guerrier déjà K.-O.).
if hp <= 0:
    raise ValueError(f"Les points de vie doivent être > 0 (reçu : {hp})")

2.7 Exercice 2 : La Classe TrainingDummy

Pour tester la compréhension des règles et des constructeurs avant de concevoir des combattants complets, vous allez développer dans src/zarena/dummy.py un mannequin d’entraînement (TrainingDummy). C’est une classe poubelle qui sert juste d’échauffement.

Cahier des charges

  1. Le constructeur __init__(self, name: str, max_hp: int) -> None :
  • Valide que max_hp > 0 (lever ValueError sinon).
  • Enregistre les attributs d’instance self.name, self.max_hp et initialise la santé courante au maximum : self.current_hp = max_hp.
  1. La méthode take_hit(self, damage: int) -> None :
  • Valide que les dégâts reçus sont positifs (damage >= 0, lever ValueError sinon).
  • Si self.current_hp == 0, lever immédiatement RuntimeError("Le mannequin est déjà pulvérisé !").
  • Réduit self.current_hp des dégâts reçus, sans jamais descendre sous zéro (\(\max(0, \text{current\_hp} - \text{damage})\)).
  1. La méthode is_broken(self) -> bool :
  • Renvoie True si self.current_hp == 0, et False sinon.

Banc d’auto-validation

Créez test_exo2.py à la racine de ~/tp-exercices/ et lancez python test_exo2.py :

# test_exo2.py
from zarena.dummy import TrainingDummy

# 1. Validation de l'invariant constructeur
try:
    TrainingDummy(name="Cible Invalide", max_hp=0)
    assert False, "Erreur : max_hp <= 0 accepté !"
except ValueError:
    pass

# 2. Test de l'encaissement et du plancher à zéro
dummy = TrainingDummy(name="Mannequin Bois", max_hp=50)
assert dummy.current_hp == 50
assert dummy.is_broken() is False

dummy.take_hit(30)
assert dummy.current_hp == 20

dummy.take_hit(40)  # Doit s'arrêter à 0, pas à -20
assert dummy.current_hp == 0
assert dummy.is_broken() is True

# 3. Test de frappe sur mannequin déjà hors service
try:
    dummy.take_hit(10)
    assert False, "Erreur : coup sur cible détruite accepté !"
except RuntimeError:
    pass

print("Exercice 2 validé avec succès !")
Question de Compréhension 1

Dans la méthode take_hit(self, damage: int), quelle différence conceptuelle y a-t-il entre le paramètre self et le paramètre damage ?

Dérouler pour afficher la solution

Partie 3 : Encapsulation, Attributs Protégés & @property (30 min)

3.1 Motivation : La Vulnérabilité des Attributs Publics

À l’issue de la Partie 2, notre classe BaseWarrior possède des attributs déclarés librement. Or, par défaut en Python, tous les attributs d’une instance sont publics. N’importe quel module ou script tiers peut écraser l’état interne d’un combattant sans passer par les méthodes autorisées :

goku = BaseWarrior("Goku", hp=100, ki=50)

# Faille 1 : Triche et corruption de santé
goku.hp = 999999  # Plus de PV que le maximum sans passer par un soin

# Faille 2 : État physique aberrant
goku.ki = -50  # Énergie négative qui corrompt les calculs d'attaques

Dans les langages comme C++ ou Java, la réponse classique consiste à déclarer la variable strictement privée (private int hp;) et à forcer l’usage d’accesseurs verbeux (getHp(), setHp(int val)).

Python privilégie une approche plus lisible : le décorateur @property, qui conserve la syntaxe naturelle d’un attribut (goku.hp = 80) tout en déléguant en coulisses la lecture et l’écriture à des méthodes de contrôle.

3.2 Le Mécanisme @property appliqué à la Santé (hp)

Pour encapsuler un attribut, on applique une convention et un décorateur standard :

  1. La convention de l’attribut protégé (_nom) : on renomme la variable interne avec un tiret bas (self._hp). Cela avertit les développeurs que cette variable relève des entrailles de la classe et ne doit jamais être manipulée directement depuis l’extérieur.
  2. Le getter (@property) : méthode portant le nom public de l’attribut (hp), qui renvoie la valeur protégée lors d’un accès en lecture.
  3. Le setter (@nom.setter) : méthode portant le même nom, qui intercepte toute affectation (guerrier.hp = nouvelle_valeur) pour valider et contraindre la valeur avant de l’enregistrer dans self._hp.
class BaseWarrior:

    def __init__(self, name: str, hp: int) -> None:
        self.name = name
        self.max_hp = hp
        # On passe par le setter dès l'initialisation !
        self.hp = hp

    @property
    def hp(self) -> int:
        """GETTER : Accès en lecture (ex: print(goku.hp))."""
        return self._hp

    @hp.setter
    def hp(self, value: int) -> None:
        """SETTER : Intercepte goku.hp = ... et borne strictement entre 0 et max_hp."""
        self._hp = max(0, min(value, self.max_hp))

Pourquoi écrire self.hp = hp dans __init__ ?

Remarquez que dans le constructeur, on écrit self.hp = hp (sans tiret bas) et non self._hp = hp.

Python détecte immédiatement la présence du setter et lui transmet l’argument. Ainsi, même à la création de l’objet, l’invariant est sanctuarisé : il est rigoureusement impossible d’instancier un guerrier avec une santé corrompue.

Partie 4 : L’Héritage — Exceptions Métier, super() & Surcharge (30 min)

4.1 Pourquoi Hériter ? Factorisation et Spécialisation

L’héritage répond au principe fondamental D.R.Y. (Don’t Repeat Yourself). En programmation objet, la syntaxe class Enfant(Parent): permet à une classe fille de récupérer automatiquement l’ensemble des attributs et méthodes de sa classe parente.

L’héritage résout deux problèmes d’ingénierie majeurs :

  1. L’infrastructure logicielle : hiérarchiser nos propres erreurs métier.
  2. Le domaine métier : modéliser des familles d’objets spécialisés (SaiyanWarrior hérite de BaseWarrior).

4.2 Première Application : Structurer nos Exceptions Métier

Jusqu’ici, nous utilisions des exceptions génériques (ValueError, RuntimeError). Mais dans un moteur de simulation complexe, une ValueError peut être déclenchée par une bibliothèque tierce (NumPy). Si nous voulons intercepter spécifiquement les incidents de notre simulateur sans étouffer les bugs système, nous devons créer notre propre arbre d’exceptions.

Toute classe qui hérite de la classe native Exception devient une exception levable avec raise.

Créez src/zarena/exceptions.py :

# src/zarena/exceptions.py


class ZArenaError(Exception):
    """Exception racine : tout incident propre au simulateur hérite d'ici."""

    pass


class InvalidStatError(ZArenaError):
    """Spécialisation : levée lorsqu'une statistique de base est illégale."""

    pass


class FighterFaintedError(ZArenaError):
    """Spécialisation : levée lorsqu'une entité K.-O. tente d'agir ou d'encaisser."""

    pass


class NotEnoughKiError(ZArenaError):
    """Spécialisation : levée lorsqu'une attaque spéciale manque de Ki."""

    pass

Pourquoi ces classes sont-elles vides (pass) ? Parce que leur valeur ne réside pas dans du nouveau code, mais dans leur identité typée au sein de l’arbre d’héritage. Un utilisateur de notre moteur pourra ainsi écrire except ZArenaError: pour intercepter n’importe quel incident du jeu en une seule clause.

Le Rôle Impératif de super().__init__()

Lorsqu’une classe fille (SaiyanWarrior) hérite de BaseWarrior, son constructeur doit obligatoirement appeler le constructeur du parent via super().__init__(...) pour garantir que name, max_hp, max_ki et attack_power soient correctement initialisés.

class SaiyanWarrior(BaseWarrior):

    def __init__(
        self,
        name: str,
        hp: int,
        ki: int = 50,
        attack_power: int = 40,
        rage_multiplier: float = 1.5,
    ) -> None:
        # Délégation de l'initialisation commune au parent
        super().__init__(name=name, hp=hp, ki=ki, attack_power=attack_power)
        # Initialisation propre à la classe fille
        self.rage_multiplier = rage_multiplier

Si cet appel est omis, les attributs parents ne sont jamais créés sur l’instance fille, provoquant un plantage immédiat dès la première consultation d’attribut.

4.4 Surcharge et Extension de Méthodes (Method Overriding)

Une classe fille peut redéfinir une méthode héritée pour enrichir son comportement :

  • Soit remplacer totalement la méthode parente.
  • Soit l’étendre en appelant super().methode() pour récupérer le résultat standard, puis en lui appliquant des règles spécifiques.

Partie 5 : Notion d’Interface & Classes Abstraites (abc.ABC) (25 min)

5.1 Qu’est-ce qu’une Interface Logicielle ?

Imaginons le moteur de match général de l’arène :

def simuler_tour(attaquant, defenseur):
    degats = attaquant.execute_attack()
    defenseur.take_damage(degats)

Si un développeur conçoit un combattant mais nomme sa méthode lancer_attaque() ou compute_damage(), le moteur de jeu explose immédiatement à l’exécution avec un AttributeError.

Une interface est un contrat de comportement pur : elle formalise ce qu’une entité doit savoir faire, sans imposer comment elle le fait. Cela permet le Polymorphisme : le moteur d’arène peut manipuler n’importe quel combattant du moment qu’il honore ce contrat.

5.2 Les Classes Abstraites avec le Module abc

Pour formaliser ce contrat, Python propose le module standard abc (Abstract Base Classes) :

  1. Une classe abstraite hérite de abc.ABC.
  2. Elle verrouille les méthodes obligatoires avec le décorateur @abstractmethod.
  3. Une classe abstraite ne peut jamais être instanciée directement.
  4. Toute sous-classe qui omet d’implémenter l’une des méthodes abstraites est immédiatement bloquée à l’instanciation par l’interpréteur.

5.3 Architecture de l’Arène : ArenaFighter \(\rightarrow\) BaseWarrior & Cyborg

Définissons dans src/zarena/arena.py le contrat suprême ArenaFighter.

Pour prouver la puissance de l’abstraction, notre arène accueillera deux familles de combattants totalement différentes mais parfaitement interopérables :

  1. Les Guerriers Biologiques (BaseWarrior) : qui gèrent leur énergie vitale (Ki).
  2. Les Combattants Mécaniques (Cyborg) : qui ne possèdent pas de jauge de Ki, mais un bouclier qui réduit passivement tous les dégâts reçus.

Partie 6 : Méthodes Spéciales (Dunders) — Intégration Native (20 min)

En Python, chaque opération native (print(), ==, len(), ()) fait appel sous le capot à une méthode dont le nom est encadré d’un double tiret bas (Double Underscore \(\rightarrow\) __dunder__).

6.1 __repr__ vs __str__

  • __repr__ (Rigueur technique) : Destiné aux développeurs dans le terminal ou les journaux de logs. Doit décrire l’objet de façon univoque : Cyborg(name='C-17', hp=55, power=60, shield=15)
  • __str__ (Affichage utilisateur) : Destiné à l’utilisateur final lors d’un print() : [C-17 | PV: 55/100 | Bouclier: 15]

6.2 Égalité Sémantique : __eq__

Par défaut, l’opérateur c1 == c2 compare l’adresse mémoire physique (c1 is c2). Deux clones créés avec exactement les mêmes caractéristiques sont donc jugés différents. Pour comparer les valeurs :

def __eq__(self, other: object) -> bool:
    if not isinstance(other, Cyborg):
        return False
    return self.name == other.name and self.hp == other.hp

6.3 Combattant Appelable : __call__

L’implémentation de __call__ permet d’utiliser l’objet directement avec des parenthèses, comme une fonction pour déclencher son assaut :

degats = c17()  # Peut être implémenté pour être l'équivalent direct à c17.execute_attack()

Vous avez acquis l’ensemble des fondements de la POO : vérification d’invariants avec raise, encapsulation via @property, hiérarchie de classes abstraites avec abc.ABC et méthodes spéciales.

Vous allez maintenant transposer exactement cette architecture au moteur de jeu de votre projet officiel : l’arène de combat Pokémon sous src/pyarena/core/.

Respect Strict des Signatures de l’Annexe Technique

Les bancs de test de la CI GitHub Actions et les protocoles d’évaluation automatisée reposent strictement sur les identifiants et signatures en anglais consignés dans l’Annexe Technique contractuelle. Toute divergence syntaxique provoquera l’échec immédiat des tests de conformité.

Étape 2 : Hiérarchie des Exceptions Métier (src/pyarena/core/exceptions.py)

Déclarez l’arborescence des exceptions du projet dérivant d’une racine unique :

# src/pyarena/core/exceptions.py


class PyArenaException(Exception):
    """Exception racine du projet PyArena."""

    pass


class FighterFaintedError(PyArenaException):
    """Levée lorsqu'une entité K.-O. (hp == 0) tente d'agir ou de subir une action invalide."""

    pass


class InvalidStatError(PyArenaException):
    """Levée lorsqu'une statistique de base ou recalculée est strictement négative ou incohérente."""

    pass


class DataFetchError(PyArenaException):
    """Levée si l'API distante est injoignable ET qu'aucun cache local n'existe sur le disque."""

    pass

Étape 3 : Classe Abstraite BaseFighter (src/pyarena/core/models.py)

Dans src/pyarena/core/models.py, déclarez l’interface formelle non instanciable en héritant de abc.ABC :

# src/pyarena/core/models.py
from abc import ABC, abstractmethod


class BaseFighter(ABC):
    """Contrat comportemental formel d'un combattant dans PyArena."""

    @property
    @abstractmethod
    def id(self) -> int:
        """Identifiant numérique officiel PokéAPI."""
        pass

    @property
    @abstractmethod
    def name(self) -> str:
        """Nom du combattant."""
        pass

    @property
    @abstractmethod
    def hp(self) -> int:
        """Points de vie courants."""
        pass

    @hp.setter
    @abstractmethod
    def hp(self, value: int) -> None:
        """Fixe les points de vie avec bornage strict [0, max_hp]."""
        pass

    @property
    @abstractmethod
    def max_hp(self) -> int:
        """Points de vie maximaux calculés au niveau 50."""
        pass

    @property
    @abstractmethod
    def attack(self) -> int:
        """Statistique d'attaque effective."""
        pass

    @property
    @abstractmethod
    def defense(self) -> int:
        """Statistique de défense effective."""
        pass

    @property
    @abstractmethod
    def speed(self) -> int:
        """Statistique de vitesse effective."""
        pass

    @property
    @abstractmethod
    def type_1(self) -> str:
        """Type élémentaire principal (ex: 'Feu', 'Eau', 'Plante', etc.)."""
        pass

    @property
    @abstractmethod
    def type_2(self) -> str | None:
        """Second type élémentaire éventuel, ou None si mono-type."""
        pass

    @abstractmethod
    def take_damage(self, amount: int) -> None:
        """Décrémente les points de vie de la valeur indiquée.

        Ne peut jamais laisser hp sous 0.
        Lève FighterFaintedError si le combattant est déjà K.-O. (hp == 0) avant l'appel.
        """
        pass

    @abstractmethod
    def is_alive(self) -> bool:
        """Retourne True si hp > 0, False sinon."""
        pass

    @abstractmethod
    def reset_stats(self) -> None:
        """Restaure les points de vie à leur valeur maximale (hp = max_hp)."""
        pass

Étape 4 : Classe Concrète Fighter (src/pyarena/core/models.py)

Dans le même fichier, implémentez la classe concrète Fighter héritant de BaseFighter :

  1. Constructeur __init__ :
def __init__(
    self,
    id: int,
    name: str,
    type_1: str,
    type_2: str | None,
    hp_base: int,
    attack_base: int,
    defense_base: int,
    speed_base: int,
) -> None:

  • Valider que l’ensemble des statistiques de base sont \(> 0\) (lever InvalidStatError si une valeur est \(\le 0\)).

  • Calculer et enregistrer les caractéristiques normalisées au Niveau 50 selon le cahier des charges :

\[\text{max\_hp} = \text{hp\_base} + 60, \quad \text{attack} = \text{attack\_base} + 5\]

\[\text{defense} = \text{defense\_base} + 5, \quad \text{speed} = \text{speed\_base} + 5\]

  • Initialiser la santé courante au maximum : self._hp = self._max_hp.
  1. Encapsulation de la Santé :
  • Dans @hp.setter, contraindre rigoureusement la valeur reçue dans l’intervalle \([0, \text{max\_hp}]\) :

\[\text{hp} \leftarrow \max(0, \min(\text{value}, \text{max\_hp}))\]

  1. Méthode take_damage(amount: int) -> None :

  • Si not self.is_alive() (combattant déjà à 0 PV), lever immédiatement FighterFaintedError.

  • Décrémenter les points de vie via le setter sans descendre sous 0.

  1. Méthode reset_stats(self) -> None :
  • Restaure self.hp à self.max_hp.
  1. Méthodes spéciales requises :

  • __repr__(self) -> str : Représentation technique non ambiguë pour le débogage, ex : Fighter(id=25, name='Pikachu', hp=95/95).

  • __str__(self) -> str : Affichage lisible pour l’utilisateur, ex : Pikachu (Électrik) - PV: 95/95.

  • __eq__(self, other: object) -> bool : Égalité basée sur la parité de l’attribut id (et la vérification d’instance isinstance(other, BaseFighter)).

Étape 5 : Structure Immuable BattleResult (src/pyarena/core/models.py)

Déclarez la structure immuable consignant le bilan d’un duel sous la forme d’une dataclass gelée :

from dataclasses import dataclass


@dataclass(frozen=True)
class BattleResult:
    winner: BaseFighter  # Instance du combattant vainqueur
    loser: BaseFighter  # Instance du combattant vaincu
    turns: int  # Nombre total de tours écoulés jusqu'au K.-O.
    remaining_hp: int  # Points de vie résiduels du vainqueur
