Objectifs et Démarche Pédagogique

Lors des séances précédentes, nous avons modélisé nos entités en programmation orientée objet (core/models) et sanctuarisé leurs comportements par des suites de tests unitaires rigoureuses (pytest). Cependant, nos combattants étaient jusqu’ici instanciés « en dur » dans le code source (BaseWarrior("Goku", 100, ...)).

Dans un système logiciel professionnel ou un projet de Data Science, les données ne sont jamais codées en dur :

  • Elles proviennent d’API REST distantes soumises aux aléas du réseau, aux pannes de serveurs et aux limitations de débit (rate-limiting).
  • Elles transitent sous des formats hétérogènes : charges utiles JSON arborescentes, matrices de coefficients (CSV) ou structures géoréférencées (GeoJSON).
  • Elles doivent être persistées localement via un patron de cache disque résilient (Cache-Aside) pour garantir la haute disponibilité et le fonctionnement hors-ligne de l’application.
  • Le défi des tests automatisés : une chaîne d’intégration continue (GitHub Actions) ne doit jamais dépendre d’une connexion Internet active ni surcharger les serveurs distants. Il est obligatoire d’apprendre à simuler (mocker) les échanges réseau.

Partie 0 : Architecture du Module io/ & Configuration

0.1 Pourquoi un Sous-Paquet io/ Dédié ?

En architecture logicielle, le principe de Séparation des Responsabilités (Separation of Concerns) impose d’isoler strictement la logique métier (nos modèles BaseWarrior, SaiyanWarrior sous core/) des mécanismes d’entrée/sortie réseau et fichier (I/O pour Input/Output).

Si l’API change d’adresse ou si le format d’un fichier CSV évolue, seuls les modules du sous-paquet io/ doivent être modifiés, sans impacter une seule ligne de nos classes de combat.

Notre arborescence s’organise ainsi :

├── data/
│   ├── styles_combat.csv     # Matrice tabulaire des multiplicateurs
│   └── arenas_dbz.geojson    # Coordonnées et métadonnées des arènes
├── src/

│       ├── warriors.py #autres fichiers (battle.py, ...)
│       └── io/               # SOUS-PAQUET D'INGESTION
│           ├── __init__.py
│           ├── fetcher.py    # Client API REST avec cache disque
│           └── loader.py     # Chargeur de fichiers tabulaires et spatiaux

Partie 1 : Le Protocole HTTP, Requêtes REST & Exceptions Réseau

1.1 Motivation : Comment Dialoguent les Systèmes Modernes ?

Pour récupérer les caractéristiques d’un guerrier stocké sur les serveurs, notre machine locale doit initier une conversation à travers le Web. Le protocole universel de cet échange est HTTP.

Une transaction REST se décompose en deux phases :

  1. La Requête Client : notre script envoie un message contenant :

    • Une méthode : GET (demande de lecture sans modification d’état).
    • Une URL d’accès : https://raw.githubusercontent.com/bbensaid30/HAX_dev_provisoire/data-api/api/warriors/1.json.
    • Des en-têtes optionnels (Headers) pour l’authentification ou le format attendu.

  2. La Réponse Serveur : le serveur renvoie :

    • Un Code de Statut HTTP numérique indiquant le sort de la requête.
    • Un corps de message (Payload), le plus souvent sous la forme d’une chaîne de caractères structurée en JSON.

Les Codes de Statut Indispensables en Data Science

  • 200 OK : Requête validée, données disponibles.
  • 404 Not Found : L’identifiant demandé n’existe pas en base.
  • 429 Too Many Requests : Quota de requêtes dépassé (blocage anti-spam).
  • 500 Internal Server Error : Incident ou plantage sur le serveur distant.

1.2 La Bibliothèque requests et l’Impératif Industriel du Timeout

En Python, la bibliothèque standard d’ingestion HTTP est requests :

import requests

url = "https://raw.githubusercontent.com/bbensaid30/HAX_dev_provisoire/data-api/api/warriors/1.json"
reponse = requests.get(url, timeout=5.0)

if reponse.status_code == 200:
    data = reponse.json()  # Décode la chaîne JSON en dictionnaire Python
    print(f"Combattant : {data['name']}")

Règle d’or en Production : Toujours définir timeout

Par défaut, si l’argument timeout est omis, requests.get() attend indéfiniment même si le serveur distant ne répond pas. Votre pipeline de données, votre boucle d’entraînement ou votre serveur web peuvent rester gelés pendant des heures. Tout appel réseau doit obligatoirement comporter un délai d’expiration (ex. timeout=5.0).

1.3 Encapsuler les Pannes Réseau dans une Exception Métier

Si la connexion Wi-Fi s’interrompt ou si le serveur distant renvoie une erreur 500, requests déclenche des exceptions internes telles que requests.exceptions.ConnectionError ou requests.exceptions.Timeout.

Un code propre applique le principe de l’Encapsulation des Exceptions : le moteur de combat ne doit pas manipuler d’exceptions réseau brutes. Le composant d’ingestion intercepte ces anomalies et lève une exception du domaine : DataFetchError.

Ajoutez cette exception dans src/zarena/exceptions.py :

# src/zarena/exceptions.py (Ajout)
class DataFetchError(ZArenaError):
    """Levée si l'API distante est injoignable ET qu'aucun cache local n'existe."""
    pass
NoteNote d’ingénierie : response.raise_for_status() vs Contrôle explicite de statut

La bibliothèque requests propose la méthode native response.raise_for_status(), qui lève une exception requests.exceptions.HTTPError dès que le code HTTP est supérieur ou égal à 400 (erreurs client 4xx et serveur 5xx).

Dans le cadre d’un client de données strict, nous préférons tester explicitement if response.status_code != 200: :

  1. Une API REST peut renvoyer un code 204 No Content : pour raise_for_status(), c’est un succès, mais l’appel ultérieur à response.json() échoue avec un JSONDecodeError.
  2. Cela garantit le respect formel du contrat d’interface : la ressource JSON demandée doit renvoyer un statut 200 OK, tout autre code déclenchant immédiatement notre exception métier DataFetchError.

1.4 Exercice 1 : Le Récepteur HTTP Distant [Guidage Moyen]

Dans src/zarena/io/fetcher.py, concevez la classe CapsuleCorpFetcher.

Cahier des charges

  1. Constructeur __init__(self, base_url: str) -> None : Enregistre l’URL racine en supprimant un éventuel slash terminal : self.base_url = base_url.rstrip("/").

  2. Méthode fetch_remote_warrior(self, warrior_id: int) -> dict :

    • Construit l’URL cible : f"{self.base_url}/warriors/{warrior_id}.json".
    • Configure un en-tête headers={"User-Agent": "ZArena-Pipeline/1.0"} pour s’identifier proprement auprès du serveur.
    • Émet la requête requests.get(url, headers=headers, timeout=5.0).
    • Si response.status_code == 200, renvoie le dictionnaire issu de response.json().
    • Si le statut est différent de 200 (ex. 204), lever DataFetchError(f"Échec API : code {response.status_code}").
    • En cas de problème de connexion (interception de requests.RequestException), lever DataFetchError en encapsulant la cause (from err).

Transition : Notre client HTTP fonctionne. Mais que se passe-t-il si nous simulons un tournoi de 10 000 combats ? Réémettre une requête HTTP pour chaque combattant saturerait le réseau et ralentirait massivement le programme. Nous devons mettre en place un cache local.

Partie 2 : Stratégie de Cache Disque (Cache-Aside Pattern)

2.1 Motivation : Pourquoi et Comment Mettre en Cache ?

Interroger le réseau pour des données immuables est une anomalie de conception :

  • Latence : Une requête HTTP prend entre 50 et 500 ms, alors qu’une lecture disque locale prend moins de 0.2 ms (un gain d’un facteur 1 000).
  • Résilience : Si le réseau se coupe pendant une simulation, les données déjà téléchargées doivent rester accessibles.
  • Sobriété : Évite de surcharger les serveurs distants ou de subir des blocages d’IP.

Le patron architectural Cache-Aside répond à ce besoin :

               ┌────────────────────────┐
               │ get_warrior_data(id)   │
               └───────────┬────────────┘
                           │
                 [Le fichier existe ?]
                OUI  /              \  NON                                    
               ▼                       ▼
    ┌──────────────────────┐   ┌──────────────────────┐
    │ Charger depuis le    │   │ Télécharger depuis   │
    │ disque local (JSON)  │   │ l'API distante       │
    └──────────────────────┘   └──────────┬───────────┘
                                          │
                               [Sauvegarder sur le disque]
                                          │
                                          ▼
                               ┌──────────────────────┐
                               │ Renvoyer les données │
                               └──────────────────────┘

2.2 Gestion des Chemins avec pathlib.Path

Pour créer et manipuler des dossiers de cache sans dépendre du système d’exploitation (Linux, macOS ou Windows), on utilise pathlib.Path :

import json
from pathlib import Path

repertoire = Path("data/cache/warriors")
repertoire.mkdir(parents=True, exist_ok=True)  # Crée l'arborescence complète si absente

fichier_cible = repertoire / "1.json"

if fichier_cible.exists():
    with open(fichier_cible, "r", encoding="utf-8") as f:
        data = json.load(f)

#json.dump(data, f, indent=) (pour l'écriture dans un fichier f)

Partie 3 : Mini-Cours Pratique : Pandas & Matrices Tabulaires

3.1 Motivation : Pourquoi Pandas ? De l’Indice Aveugle à l’Étiquette Sémantique

Dans l’arène de combat, les dégâts d’une attaque dépendent de l’affinité entre la nature de l’attaque portée et la physiologie de la cible :

  • Une frappe physique (Corps-à-corps) est absorbée par le blindage d’un Cyborg (\(\times 0{,}5\)).
  • Une décharge d’énergie (Ki) transperce un combattant ordinaire (\(\times 1{,}5\)) mais est absorbée par un Cyborg (\(\times 0{,}5\)).
  • Une technique occulte (Magie) contourne les blindages technologiques (\(\times 2{,}0\)).

Si nous stockions cette table dans un tableau NumPy brut \(A \in \mathbb{R}^{4 \times 4}\) :

multiplicateur = A[1, 3]  # Que représentent l'indice 1 et l'indice 3 ?

Le code devient opaque, impossible à relire et vulnérable aux inversions ligne/colonne.

Pandas résout ce problème d’ingénierie en introduisant l’indexation nommée : chaque ligne et chaque colonne est identifiée par une étiquette explicite.

3.2 Intégration sans Rupture de Compatibilité avec warriors.py

Comment cette matrice s’articule-t-elle avec le code existant de warriors.py sans casser les classes ou les tests précédents ?

  1. Aucun changement sur take_damage(self, amount: int) : la méthode continue de recevoir un montant brut de dégâts entiers. Pour Cyborg, le blindage shield continue de s’appliquer en réduction finale.

  2. Attribut race rétro-compatible : nos classes de combattants définissent simplement un attribut ou une propriété race avec une valeur par défaut cohérente :

    • BaseWarrior possède self.race: str = "Terrien".
    • SaiyanWarrior possède self.race: str = "Saiyan".
    • Cyborg possède self.race: str = "Cyborg". Toutes les signatures existantes restent valides : BaseWarrior("Krilin", 100) fonctionne exactement comme avant.

  3. Le calcul d’assaut modulé : lors d’un affrontement, le moteur de match calcule : \[\text{dégâts effectifs} = \lfloor \text{attaquant.execute\_attack()} \times \text{multiplicateur} \rfloor\] puis transmet ce montant à défenseur.take_damage(dégâts effectifs).

3.3 Les Deux Objets Fondamentaux de Pandas & Sélection .loc

  1. La Series : Un tableau unidimensionnel indexé (une colonne nommée).
  2. Le DataFrame : Une table bidimensionnelle composée de plusieurs Series partageant le même index de lignes.

Créez le fichier data/styles_combat.csv :

ou charger le depuis le dépôt

Chargeons cette matrice avec Pandas en désignant la première colonne comme index des lignes :

Affichage console :

               Terrien  Saiyan  Namek  Cyborg
style                                        
Corps-a-corps      1.0     1.0    1.2     0.5

Pour extraire une valeur à l’intersection d’une ligne et d’une colonne étiquetées, on utilise .loc[ligne, colonne] :

coeff = float(df.loc["Magie", "Cyborg"])  # Renvoie exactement 2.0
NotePerformance en Simulation Massive : Du DataFrame au Dictionnaire Imbriqué

L’indexation .loc de Pandas apporte confort et sécurité lors du chargement, du filtrage ou de l’affichage ponctuel d’une confrontation dans Streamlit. En revanche, dans une boucle de Monte-Carlo exécutant \(100\,000\) duels, répéter .loc induit un surcoût sensible (environ \(50\) fois plus lent que l’acccès dictionnaire).

La bonne pratique d’ingénierie logicielle consiste à :

  1. Valider et ingérer la matrice tabulaire via Pandas au chargement (pd.read_csv).
  2. Pré-convertir la matrice en dictionnaire Python natif imbriqué via df.to_dict(orient="index").
  3. Réaliser des lectures directes en \(O(1)\) dans la boucle de simulation : lookup[style_attaque][race_defenseur].

Partie 4 : Ingestion de Données Spatiales : Le Format GeoJSON

4.1 Motivation : Qu’est-ce que le GeoJSON et à quoi sert-il ?

Les tournois ne se déroulent pas dans le vide : ils prennent place dans des arènes réparties sur le territoire. Dans le jalon final, ces arènes seront projetées sur une carte interactive via Streamlit et Folium.

Faut-il installer des bibliothèques cartographiques lourdes (GDAL, GeoPandas) pour lire ces données ? Absolument pas.

Le format GeoJSON (IETF RFC 7946) n’est rien d’autre qu’un fichier texte JSON standard qui organise les données géographiques selon une nomenclature universelle :

{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "geometry": {
        "type": "Point",
        "coordinates": [3.8767, 43.6108]  // ATTENTION : [Longitude, Latitude]
      },
      "properties": {
        "id": "arena-01",
        "name": "Arène de Montpellier",
        "capacity": 15000
      }
    }
  ]
}
ImportantLe Piège d’Intégration Cartographique : GeoJSON vs Folium / Leaflet
  • Norme GeoJSON (RFC 7946) : L’ordre des coordonnées géométriques suit l’axe cartésien standard \([X, Y]\), soit impérativement [Longitude, Latitude].
  • Bibliothèques de cartographie (Folium, Leaflet) : Les fonctions de tracé (comme folium.Marker) exigent l’ordre géographique traditionnel : [Latitude, Longitude].

Pour sanctuariser le pipeline et éviter toute inversion lors du développement du tableau de bord (Streamlit), le module de chargement doit isoler la conversion [lon, lat] -> (lat, lon).

Partie 5 : Tests Unitaires Isolés & Mocking Réseau (requests-mock)

5.1 Pourquoi « Mocker » le Réseau dans les Tests ?

Considérons ce test naïf :

def test_recuperation_goku():
    fetcher = CapsuleCorpFetcher("https://api.capsulecorp.com")
    data = fetcher.get_warrior_data(1)
    assert data["name"] == "Son Goku"

Ce test présente trois défauts majeurs :

  1. Instabilité : Si le serveur de la Capsule Corp est en maintenance, le test échoue alors que notre code fonctionne parfaitement.
  2. Lenteur : Exécuter 100 requêtes HTTP dans une suite de tests allonge le temps d’exécution de plusieurs minutes.
  3. Impossibilité de tester les pannes : Comment vérifier que notre gestionnaire d’erreurs intercepte bien une panne HTTP 500 sans faire crasher le vrai serveur de production ?

La Solution : Le Mocking.
Un Mock est un intercepteur logiciel qui intercepte les requêtes requests.get() au sein même du processus Python et renvoie une réponse préenregistrée en mémoire vive, sans qu’aucun paquet réseau ne soit émis.

5.2 Utilisation de la Fixture requests_mock

Grâce au paquet requests-mock, Pytest fournit la fixture requests_mock :

def test_interception_reseau(requests_mock):
    # 1. Configuration du simulateur : intercepter cette URL précise
    url = "https://api.test.com/warriors/1.json"
    requests_mock.get(url, json={"name": "Son Goku", "hp_base": 120}, status_code=200)

    # 2. Exécution du vrai code métier
    reponse = requests.get(url, timeout=5.0)

    # 3. La réponse est instantanée et provient de la mémoire
    assert reponse.json()["name"] == "Son Goku"

NoteComprendre et Décoder la Structure JSON Imbriquée de PokéAPI

Lorsque vous appelez votre méthode fetcher.get_pokemon(pokemon_id) (ou directement response.json()), l’API PokéAPI renvoie un volumineux dictionnaire Python racine que l’on nomme ici payload (la « charge utile » de la réponse HTTP).

Contrairement à des données tabulaires simples, l’API ne stocke pas directement payload["hp"] ou payload["attack"]. Les données sont fortement imbriquées dans des sous-listes de dictionnaires.

1. Anatomie de la clé payload["stats"]

Dans la réponse de l’API pour Pikachu (id = 25), la clé "stats" est associée à une liste de 6 dictionnaires (un par caractéristique) ayant la structure suivante :

{
  "id": 25,
  "name": "pikachu",
  "stats": [
    {
      "base_stat": 35,
      "effort": 0,
      "stat": {
        "name": "hp",
        "url": "[https://pokeapi.co/api/v2/stat/1/](https://pokeapi.co/api/v2/stat/1/)"
      }
    },
    {
      "base_stat": 55,
      "effort": 2,
      "stat": {
        "name": "attack",
        "url": "[https://pokeapi.co/api/v2/stat/2/](https://pokeapi.co/api/v2/stat/2/)"
      }
    },
    {
      "base_stat": 40,
      "effort": 0,
      "stat": {
        "name": "defense",
        "url": "[https://pokeapi.co/api/v2/stat/3/](https://pokeapi.co/api/v2/stat/3/)"
      }
    },
    {
      "base_stat": 90,
      "effort": 0,
      "stat": {
        "name": "speed",
        "url": "[https://pokeapi.co/api/v2/stat/6/](https://pokeapi.co/api/v2/stat/6/)"
      }
    }
  ]
}

Pour chaque élément s de la liste payload[“stats”] :

  • s[“base_stat”] est un entier représentant la valeur numérique brute de la statistique.
  • s[“stat”] est un sous-dictionnaire dont le champ “name” contient la désignation textuelle en minuscules (“hp”, “attack”, “defense”, “speed”…).

Pour transformer cette liste imbriquée en un dictionnaire plat et directement indexable par nom, on utilise une compréhension de dictionnaire :

# payload est le dictionnaire renvoyé par get_pokemon(id)
payload = fetcher.get_pokemon(25)

# Extraction aplatie : chaque élément s produit la paire { "nom_stat": valeur }
raw_stats = {s["stat"]["name"]: s["base_stat"] for s in payload["stats"]}
#L'objet résultant raw_stats est un dictionnaire à plat
# raw_stats = {'hp': 35, 'attack': 55, 'defense': 40, 'special-attack': 50, 'special-defense': 50, 'speed': 90}

#Vous pouvez ensuite extraire les caractéristiques nécessaires au constructeur de Fighter sans risque d'erreur d'indice :
hp_base = raw_stats["hp"]
attack_base = raw_stats["attack"]
defense_base = raw_stats["defense"]
speed_base = raw_stats["speed"]
  1. Anatomie de la clé payload[“types”] et Règle des Slots

La clé payload[“types”] contient elle aussi une liste de dictionnaires, où chaque entrée associe un type élémentaire à un ordre d’apparition (slot) :

{
  "name": "charizard",
  "types": [
    {
      "slot": 1,
      "type": {
        "name": "fire",
        "url": "[https://pokeapi.co/api/v2/type/10/](https://pokeapi.co/api/v2/type/10/)"
      }
    },
    {
      "slot": 2,
      "type": {
        "name": "flying",
        "url": "[https://pokeapi.co/api/v2/type/3/](https://pokeapi.co/api/v2/type/3/)"
      }
    }
  ]
}
  • Règle des slots : Conformément à l’Annexe Technique, le type principal type_1 est impérativement celui avec slot == 1. Si la créature possède un second type, il est assigné à slot == 2 (sinon type_2 vaut None).
  • Traduction Anglais → Français : PokéAPI renvoie des noms anglais en minuscules (“fire”, “water”), alors que la matrice tabulaire data/types.csv utilise le français capitalisé (“Feu”, “Eau”).

On procède donc en deux temps : un dictionnaire de correspondance, puis une extraction ordonnée par slot :

# Table de correspondance bilingue officielle
TYPE_TRANSLATION: dict[str, str] = {
    "normal": "Normal", "fire": "Feu", "water": "Eau",
    "grass": "Plante", "electric": "Électrik", "ice": "Glace",
    "fighting": "Combat", "poison": "Poison", "ground": "Sol",
    "flying": "Vol", "psychic": "Psy", "bug": "Insecte",
    "rock": "Roche", "ghost": "Spectre", "dragon": "Dragon",
    "steel": "Acier", "dark": "Ténèbres", "fairy": "Fée",
}

# Dictionnaire associant chaque numéro de slot au type français correspondant :
# slots = {1: "Feu", 2: "Vol"} pour Dracaufeu
slots = {
    t["slot"]: TYPE_TRANSLATION.get(t["type"]["name"], t["type"]["name"].capitalize())
    for t in payload["types"]
}

type_1: str = slots[1]
type_2: str | None = slots.get(2, None)

Grâce à slots.get(2, None), si le Pokémon est mono-type (comme Pikachu), la clé 2 n’existe pas et type_2 reçoit la valeur None, respectant le contrat d’interface de Fighter.
