Objectifs et Démarche Pédagogique

Jusqu’à présent, l’ensemble de nos développements s’exécutait exclusivement dans un terminal texte : nos simulations de combat Z-Arena, nos estimations de Monte-Carlo parallélisées et nos chargements de données affichaient des nombres bruts dans la console.

Or, dans le monde professionnel (Data Science, Recherche Opérationnelle, Ingénierie Numérique), un modèle mathématique ou un simulateur enfermé dans un terminal n’a que peu d’impact décisionnel :

  • En Science des Données (SSD) : Un directeur produit, un médecin ou un responsable marketing ne lancera jamais un script Python en ligne de commande. Pour qu’un modèle soit adopté, il faut lui offrir une interface graphique intuitive permettant d’explorer les données, de tester des scénarios et de visualiser les incertitudes.
  • En Modélisation & Analyse Numérique (MANU) : Lorsqu’on étudie un système dynamique ou une équation aux dérivées partielles, pouvoir faire varier un paramètre physique à la souris (viscosité, pas de temps, condition initiale) et observer instantanément l’évolution des courbes accélère considérablement l’analyse qualitative par rapport à la génération manuelle de dizaines de fichiers PNG statiques.
  • Le verrou du développement Web traditionnel : Concevoir une application web classique exige de maîtriser trois langages distincts (HTML pour la structure, CSS pour la mise en page, JavaScript pour l’interactivité) en plus d’un serveur backend (FastAPI, Flask ou Django).

L’écosystème Python moderne (Streamlit, Plotly, Folium) lève ce verrou en permettant à un ingénieur ou un scientifique de bâtir une application web interactive complète en pur Python, tout en conservant une architecture logicielle rigoureuse.

Partie 0 : Du Terminal au Navigateur — Architecture Web & Découplage (25 min)

Avant de manipuler les widgets graphiques, comprenons ce qui se passe techniquement lorsque vous lancez une application web Python.

0.1 Anatomie d’une Application Web : Client vs Serveur

Lorsque vous exécutez un script Python classique (python script.py), le programme lit vos instructions, affiche du texte dans le terminal et s’arrête.

Lorsque vous lancez une application Streamlit (streamlit run app/main.py), vous démarrez un serveur web local :

   ORDINATEUR DE L'UTILISATEUR (ou Serveur Cloud)
 ┌─────────────────────────────────────────────────────────────────────────┐
 │                                                                         │
 │   ┌───────────────────────────────┐     Protocole HTTP / WebSocket      │
 │   │      NAVIGATEUR WEB           │  ◄───────────────────────────────►  │
 │   │   (Chrome, Firefox, Edge)     │     1. Envoie les clics / curseurs  │
 │   │                               │     2. Reçoit le rendu HTML/JS      │
 │   │   "Le Client" (Interface)     │                                     │
 │   └───────────────────────────────┘                                     │
 │                                                                         │
 │                                     ┌───────────────────────────────┐   │
 │                                     │      SERVEUR PYTHON           │   │
 │                                     │   (Processus Streamlit)       │   │
 │                                     │                               │   │
 │                                     │   Exécute app/main.py         │   │
 │                                     │   Appelle le package zarena   │   │
 │                                     │   "Le Backend" (Calculs)      │   │
 │                                     └───────────────────────────────┘   │
 └─────────────────────────────────────────────────────────────────────────┘
  • Le Serveur (Backend Python) : C’est le processus Python qui tourne dans votre terminal. Il écoute sur un port réseau local (par défaut localhost:8501), exécute vos calculs NumPy/Monte-Carlo et prépare les données à afficher.
  • Le Client (Navigateur Web) : C’est votre navigateur. Il ne fait aucun calcul Python : il reçoit des instructions graphiques via une connexion persistante (WebSocket) et dessine les boutons, les graphiques Plotly et les cartes Folium à l’écran.

0.2 Règle d’Architecture : Séparation Stricte src/ vs app/

C’est la règle d’or du génie logiciel appliquée aux interfaces : l’interface graphique ne doit contenir aucune logique métier ni aucune formule mathématique.

tp-exercices/
├── pyproject.toml
├── data/
│   └── arenas_dbz.geojson
├── src/
│   └── zarena/                   <── LE CŒUR MÉTIER (Indépendant de toute interface)
│       ├── warriors.py           (Modèles POO : SaiyanWarrior, Cyborg)
│       ├── battle.py             (Moteur de combat)
│       ├── parallel_engine.py    (Simulateur Monte-Carlo multi-cœurs)
│       └── io/
│           └── loader.py         (Chargement GeoJSON & extraction coordonnées)
└── app/                          <── LA COUCHE DE PRÉSENTATION (Streamlit)
    ├── charts.py                 (Fonctions de création de graphiques Plotly)
    ├── map_utils.py              (Fonctions de création de cartes Folium)
    └── main.py                   (Point d'entrée Streamlit : widgets et mise en page)

Pourquoi ce découplage est-il vital ?

  1. Testabilité : Vos tests pytest valident src/zarena/ sans avoir besoin de lancer un navigateur web.
  2. Réutilisabilité : Si demain vous remplacez Streamlit par une API REST (FastAPI) ou un script en ligne de commande, votre moteur de calcul dans src/zarena/ fonctionne sans modifier une seule ligne.

0.4 Expérience 0 : Première Page et Structuration de l’Espace (10 min)

Une interface professionnelle ne présente pas une longue colonne indigeste de texte. Streamlit fournit des conteneurs de mise en page inspirés du design web moderne :

  • st.set_page_config(...) : Configure le titre de l’onglet du navigateur et active le mode pleine largeur (layout="wide"). Doit impérativement être la première commande Streamlit du fichier.
  • st.sidebar : Crée un panneau latéral rétractable idéal pour regrouper tous les paramètres de contrôle (sélection des combattants, curseurs).
  • st.columns(n) : Découpe l’écran horizontalement en \(n\) colonnes côte à côte.
  • st.tabs(["Onglet 1", "Onglet 2"]) : Organise l’application en onglets thématiques.
  • st.metric(label, value, delta) : Affiche un indicateur clé de performance (KPI) grand format avec une flèche de variation.

Créez app/hello_app.py et testez ces composants :

# app/hello_app.py
import streamlit as st

# 1. Configuration globale de la page (toujours en premier !)
st.set_page_config(
    page_title="Z-Arena — Tableau de Bord",
    layout="wide",
)

# 2. En-tête principal
st.title("Simulateur Stochastique Z-Arena")
st.markdown("Interface décisionnelle d'analyse des affrontements du *Cell Game*.")

# 3. Panneau latéral de configuration
with st.sidebar:
    st.header("Paramètres du Duel")
    n_sims = st.slider("Nombre de simulations", min_value=100, max_value=10_000, value=1_000, step=100)
    st.info(f"Configuration prête pour {n_sims} duels.")

# 4. Affichage en colonnes et indicateurs KPI
col1, col2, col3 = st.columns(3)
col1.metric(label="Combattant 1", value="Son Gohan SSJ2", delta="Attaque +25%")
col2.metric(label="Combattant 2", value="Perfect Cell", delta="Bouclier 10")
col3.metric(label="Volume Monte-Carlo", value=f"{n_sims:,} duels")

Lancez le serveur dans votre terminal :

streamlit run app/hello_app.py

Ouvrez l’URL locale affichée (http://localhost:8501) et déplacez le curseur dans la barre latérale : observez la mise à jour instantanée des métriques.

Transition : Ce premier essai semble magique. Mais comment Streamlit parvient-il à mettre à jour l’écran dès que vous bougez un curseur ? Comprendre son moteur d’exécution est indispensable pour éviter le piège n°1 des débutants.

Partie 1 : Le Paradigme Réactif & La Mémoire (35 min)

1.1 Le Modèle d’Exécution Réactif (Top-to-Bottom Rerun)

Contrairement à une interface graphique classique (comme Tkinter ou Qt) où l’on attache des fonctions callbacks à chaque bouton, Streamlit adopte un modèle d’exécution déclaratif et réactif (proche de la philosophie de React en JavaScript) :

À chaque fois que l’utilisateur interagit avec un widget (clic sur un bouton, déplacement d’un curseur, choix dans une liste), Streamlit réexécute l’intégralité de votre script Python de la première à la dernière ligne !

  [ Action Utilisateur : déplacement du curseur ]
                        │
                        ▼
  ┌───────────────────────────────────────────┐
  │  Streamlit relance app/main.py depuis la  │
  │  ligne 1 jusqu'à la fin du fichier !      │
  │                                           │
  │  • Les variables Python locales sont      │
  │    recalculées ou réinitialisées.         │
  │  • La valeur du widget est mise à jour.   │
  └─────────────────────┬─────────────────────┘
                        │
                        ▼
  [ Mise à jour différentielle de l'écran ]

Les Deux Conséquences Directes de ce Modèle :

  1. L’amnésie des variables locales : Une variable ordinaire score = 0 écrite dans le script est remise à 0 à chaque clic !
  2. Le risque de recalcul inutile : Si vous appelez une fonction lente (run_parallel_monte_carlo sur \(50\,000\) duels ou téléchargement réseau) directement dans le flux du script, elle sera relancée à chaque fois que l’utilisateur clique sur n’importe quel bouton de la page !

1.2 Expérience 1 : Le Piège du Compteur et st.session_state (15 min)

Pour conserver des données en mémoire entre deux réexécutions du script (par exemple : l’historique des tours d’un combat en direct ou un compteur d’actions), Streamlit fournit un dictionnaire persistant attaché à l’onglet du navigateur de l’utilisateur : st.session_state.

Créez app/demo_state.py pour observer la différence entre une variable classique et st.session_state :

# app/demo_state.py
import streamlit as st

st.title("Démonstration : Variable Locale vs Session State")

# --- APPROCHE 1 : VARIABLE PYTHON CLASSIQUE (ÉCHEC) ---
compteur_naif = 0
if st.button("Incrémenter le compteur naïf"):
    compteur_naif += 1
st.write(f"Compteur naïf (remis à zéro à chaque rerun) : **{compteur_naif}**")

st.divider()

# --- APPROCHE 2 : PERSISTANCE VIA st.session_state (SUCCÈS) ---
# 1. Initialisation uniquement lors de la toute première visite
if "compteur_persistant" not in st.session_state:
    st.session_state["compteur_persistant"] = 0

# 2. Modification de l'état lors du clic
if st.button("Incrémenter le compteur persistant"):
    st.session_state["compteur_persistant"] += 1

st.write(f"Compteur persistant (conservé en mémoire) : **{st.session_state['compteur_persistant']}**")

Testez ce script avec streamlit run app/demo_state.py : cliquez plusieurs fois sur chacun des deux boutons pour constater l’amnésie de la variable locale face à la persistance de st.session_state.

1.3 La Mise en Cache Applicative : @st.cache_data vs @st.cache_resource

Dans le TP sur l’I/O, nous avons implémenté un cache disque (data/cache/*.json) pour éviter de re-télécharger les données depuis l’API distante.
Dans une application web interactive, nous devons ajouter un cache en mémoire vive (RAM) pour éviter de relancer des calculs coûteux lors des réexécutions de l’interface.

Streamlit propose deux décorateurs complémentaires :

Décorateur Usage recommandé Mécanisme interne Exemples concrets
@st.cache_data Données et Résultats de Calcul (DataFrames, dictionnaires, listes, résultats Monte-Carlo) Mémoïsation (technique d’optimisation consistant à stocker le résultat d’un appel de fonction pur dans un dictionnaire indexé par l’empreinte des arguments, à ne pas confondre avec « mémorisation »). Si la fonction est rappelée avec les mêmes arguments, Streamlit renvoie instantanément une copie du résultat stocké en RAM sans exécuter la fonction. Chargement d’un CSV/GeoJSON, exécution de run_parallel_monte_carlo(f1, f2, n_sims).
@st.cache_resource Objets Partagés Non Sérialisables (Connexions bases de données, modèles ML chargés en GPU) Singleton. Conserve l’objet unique en mémoire vive et le partage directement entre tous les utilisateurs sans le copier. Connexion SQL, modèle PyTorch/HuggingFace de 2 Go.
AstuceExemple d’Enrobage d’un Moteur de Calcul avec @st.cache_data 
@st.cache_data(show_spinner="Simulation Monte-Carlo en cours...")
def cached_monte_carlo(f1_name: str, f2_name: str, n_sims: int, seed: int) -> dict:
    # Cette fonction lourde ne s'exécute QUE si l'un des 4 paramètres change !
    ...

Note pédagogique : Passez des paramètres simples et hachables (int, str, float, tuple) aux fonctions décorées par @st.cache_data afin que Streamlit calcule leur empreinte sans erreur.

Partie 2 : Visualisation Scientifique Interactive avec Plotly (40 min)

2.1 Pourquoi Plotly plutôt que Matplotlib dans une Application Web ?

  • Matplotlib produit des images matricielles statiques (.png). C’est l’outil idéal pour figer une figure dans un article scientifique LaTeX ou un rapport PDF. Mais sur le web, l’utilisateur ne peut ni zoomer, ni isoler une courbe, ni lire la valeur exacte d’un point au survol de la souris.
  • Plotly repose sur la bibliothèque JavaScript plotly.js. Python génère une spécification déclarative en JSON que le navigateur web rend en vectoriel interactif (SVG / WebGL). L’utilisateur dispose nativement du zoom, du panoramique, des infobulles dynamiques (hover tooltips) et de l’export d’image.

Les Deux Niveaux d’API et leur Syntaxe Essentielle :

1. plotly.express (import plotly.express as px) — L’API rapide de haut niveau

Permet de créer un graphique complet en un seul appel de fonction :

import plotly.express as px

# Créer un histogramme à partir d'une liste de nombres
fig = px.histogram(
    x=ma_liste_valeurs,
    nbins=15,                                       # Nombre de barres (classes)
    title="Titre du graphique",
    labels={"x": "Nom de l'axe X", "y": "Nom de l'axe Y"},
)

# Ajouter une ligne verticale repère (ex: la moyenne)
fig.add_vline(
    x=valeur_moyenne,
    line_dash="dash",                               # Style pointillé
    line_color="red",
    annotation_text="Moyenne",                      # Étiquette affichée sur la ligne
)

# Personnaliser la mise en page globale
fig.update_layout(yaxis_title="Fréquence", template="plotly_white")

2. plotly.graph_objects (import plotly.graph_objects as go) — L’API modulaire de bas niveau

Permet d’assembler des graphiques complexes couche par couche (comme les diagrammes radar) :

import plotly.graph_objects as go

# 1. Créer une figure vierge
fig = go.Figure()

# 2. Ajouter une couche (trace) polaire (diagramme radar)
fig.add_trace(
    go.Scatterpolar(
        r=[100, 80, 60, 100],                       # Rayons (valeurs numériques)
        theta=["PV", "Attaque", "Défense", "PV"],   # Angles (noms des axes, fermé sur le 1er)
        fill="toself",                              # Remplissage coloré intérieur
        name="Nom de la série",
    )
)

# 3. Configurer les axes polaires et le titre
fig.update_layout(
    polar=dict(radialaxis=dict(visible=True)),
    title="Comparaison Radar",
)

Pour afficher une figure dans Streamlit : st.plotly_chart(fig, width="stretch").

2.2 Exercice 1 : Télémétrie Interactive des Combats Z-Arena (30 min)

Problématique

Dans notre simulateur Z-Arena, connaître uniquement le taux de victoire moyen (\(\hat{p} = 0.62\)) masque la dynamique du combat : le match se termine-t-il en 2 tours expéditifs ou en une bataille d’usure de 25 tours ?

Cahier des Charges

Dans un fichier app/charts.py, implémentez deux fonctions pures (sans appel Streamlit à l’intérieur, afin de garder les fonctions testables) :

  1. plot_turns_distribution(turns_list: list[int], f1_name: str, f2_name: str) -> go.Figure :

    • Calcule la moyenne mean_turns = float(np.mean(turns_list)).
    • Crée l’histogramme via px.histogram (nbins=15, titre explicite incluant f1_name et f2_name).
    • Ajoute une ligne verticale rouge pointillée à x=mean_turns via fig.add_vline(...).
    • Retourne fig.

  2. plot_fighters_radar(f1_stats: dict[str, int], f2_stats: dict[str, int], f1_name: str, f2_name: str) -> go.Figure :

    • Extrait les noms des caractéristiques (categories = list(f1_stats.keys())).
    • Astuce géométrique : Pour que le polygone du radar soit proprement fermé, répétez le premier élément à la fin des listes theta et r (ex. categories_closed = categories + [categories[0]]).
    • Instancie fig = go.Figure() et ajoute deux traces go.Scatterpolar (fill="toself") pour f1_name et f2_name.
    • Retourne fig.

Banc d’auto-validation immédiate

Ajoutez ce bloc tout en bas de app/charts.py et lancez python app/charts.py pour ouvrir immédiatement vos deux graphiques interactifs dans votre navigateur :

if __name__ == "__main__":
    # Test visuel immédiat des deux fonctions
    fig_hist = plot_turns_distribution([4, 5, 6, 6, 7, 8, 5, 9, 10, 6], "Gohan", "Cell")
    fig_hist.show()

    s1 = {"PV Max": 150, "Attaque": 65, "Ki": 100}
    s2 = {"PV Max": 160, "Attaque": 60, "Ki": 80}
    fig_rad = plot_fighters_radar(s1, s2, "Gohan", "Cell")
    fig_rad.show()

Partie 3 : Cartographie Géospatiale Web avec Folium (40 min)

3.1 Comment Fonctionne une Carte Web Interactive ?

Lorsque vous consultez une carte numérique (OpenStreetMap, Google Maps), le navigateur n’affiche pas une image unique géante. Il assemble dynamiquement une mosaïque de petites images carrées de \(256 \times 256\) pixels appelées des tuiles (tiles), téléchargées à la demande selon votre niveau de zoom.

  • Leaflet.js : C’est la bibliothèque JavaScript open-source de référence mondiale pour afficher ces tuiles et superposer des marqueurs vectoriels.
  • Folium : C’est une bibliothèque Python qui génère le code HTML/JavaScript Leaflet à partir de vos données Python.
  • streamlit-folium : C’est le pont qui intègre une carte Folium dans une page Streamlit via la fonction st_folium(carte, width=..., height=...).

La Syntaxe Essentielle de Folium :

import folium

# 1. Créer la carte vierge centrée sur [Latitude, Longitude]
carte = folium.Map(
    location=[43.6108, 3.8767],       # ATTENTION : [Latitude, Longitude] !
    zoom_start=6,                     # Niveau de zoom initial (1 = monde, 12 = ville)
    tiles="OpenStreetMap",         # Fond de carte épuré
)

# 2. Ajouter un marqueur ponctuel sur la carte
folium.Marker(
    location=[43.6108, 3.8767],
    popup="Texte affiché au clic sur le marqueur",
    tooltip="Texte affiché au survol de la souris",
    icon=folium.Icon(color="green", icon="star"),  # Couleurs : 'red', 'blue', 'green', 'orange'...
).add_to(carte)

# 3. Sauvegarder la carte en fichier autonome pour la tester dans un navigateur
carte.save("ma_carte.html")

Rappel Critique du TP I/O : L’Inversion des Coordonnées !

La solution propre consiste à enrichir légèrement le retour de src/zarena/ pour qu’il expose directement la durée des combats en plus du taux de victoire (exactement comme le contrat de PyArena).

  2. Dans src/zarena/battle.py : Faites en sorte que simulate_duel_step(f1, f2, rng) retourne le tuple (winner, turns) au lieu du seul vainqueur :

    def simulate_duel_step(
    f1: ArenaFighter, f2: ArenaFighter, rng: np.random.Generator
) -> tuple[int, int]:
    """Simule un duel complet et retourne (winner_id, turns)."""
    f1.reset_stats()
    f2.reset_stats()
    turns = 0
    while not f1.is_defeated() and not f2.is_defeated():
        turns += 1
        crit1 = 1.5 if rng.random() < 0.10 else 1.0
        dmg1 = max(1, int(f1.execute_attack() * rng.uniform(0.85, 1.15) * crit1))
        f2.take_damage(dmg1)
        if f2.is_defeated():
            return 1, turns

        crit2 = 1.5 if rng.random() < 0.10 else 1.0
        dmg2 = max(1, int(f2.execute_attack() * rng.uniform(0.85, 1.15) * crit2))
        f1.take_damage(dmg2)
        if f1.is_defeated():
            return 2, turns
    return (1 if not f1.is_defeated() else 2), turns

  3. Dans src/zarena/parallel_engine.py : Mettez à jour _monte_carlo_worker pour qu’il collecte les durées de son lot (turns_list: list[int]) et retourne (f1_wins, turns_list). Dans run_parallel_monte_carlo, agrégez l’ensemble des durées dans all_turns et ajoutez les clés "turns": all_turns et "turns_mean": float(np.mean(all_turns)) au dictionnaire retourné.

Pourquoi joblib et non ProcessPoolExecutor sous Streamlit (macOS / Windows) ?

Sous macOS et Windows, le module standard multiprocessing utilise la méthode spawn : chaque worker démarre un nouvel interpréteur vierge et tente de réimporter le module principal (__main__).
Or, sous Streamlit, __main__ n’est pas app/main.py, mais le lanceur CLI de Streamlit exécuté dans un fil secondaire (ScriptRunner), ce qui provoque l’arrêt brutal des workers (BrokenProcessPool).

La solution : Utilisez backend="joblib" lors de l’appel à run_parallel_monte_carlo. Le moteur loky de joblib a été conçu spécifiquement pour les environnements interactifs (Jupyter, Streamlit) : il démarre des processus travailleurs propres sans réimporter __main__, garantissant un fonctionnement identique sur Linux, macOS et Windows.

1. Architecture Multipages : Comment Fonctionnent app/main.py et app/pages/ ?

Dans le cours-TP (Z-Arena), nous avons regroupé deux vues dans un seul fichier app/main.py grâce à des onglets (st.tabs). Pour un projet complet comportant 4 à 5 modules développés en équipe de 3 ou 4 étudiants, placer tout le code dans main.py créerait un fichier monolithique illisible et multiplierait les conflits de fusion Git.

Streamlit résout ce problème grâce à un mécanisme natif de routage automatique par fichiers (Multipage Apps) :

pyarena/
├── pyproject.toml                  # Déclare src/ et app/, ainsi que la commande pyarena-app
├── src/pyarena/                    # Moteur pur (core, io, simulation, extensions)
└── app/
    ├── __init__.py
    ├── main.py                     # Page d'accueil (lanceur)
    ├── utils.py                    # Fonctions partagées (graphiques Plotly, cartes Folium)
    └── pages/                      # Dossier détecté AUTOMATIQUEMENT par Streamlit
        ├── 1_Simulateur_Duel.py    # Module 1 : Combat & Monte-Carlo
        ├── 2_Catalogue_EDA.py      # Module 2 : Exploration statistique
        ├── 3_Carte_Occitanie.py    # Module 3 : Carte Folium des 30 arènes
        ├── 4_Synergie_Equipe.py    # Module 4 : Analyseur de trio (Groupes de 4 / Bonus G3)
        └── 5_Extension.py          # Module 5 : Vues Macro & Micro de votre extension

Règles de Fonctionnement de app/pages/ :

  1. Détection automatique : Dès que vous lancez streamlit run app/main.py (ou pyarena-app), Streamlit inspecte automatiquement le sous-dossier app/pages/ et génère un menu de navigation latéral contenant main ainsi que chaque fichier .py présent dans pages/.
  2. Convention de nommage : Le préfixe numérique fixe l’ordre d’affichage dans le menu, et les underscores (_) sont convertis en espaces (par exemple, 1_Simulateur_Duel.py s’affiche sous le nom « Simulateur Duel »).
  3. Indépendance et partage de mémoire : Chaque fichier dans app/pages/ est un script Python autonome qui importe ses dépendances (from pyarena..., from app.utils import ...). En revanche, toutes les pages d’une même session partagent automatiquement le même dictionnaire st.session_state et le même cache @st.cache_data.
  4. Organisation Git idéale : Chaque membre de l’équipe peut développer sa page dédiée en parallèle sans toucher aux fichiers des autres coéquipiers.

Exemple Concret : Articulation entre app/main.py et app/pages/

Une erreur fréquente consiste à vouloir importer 1_Simulateur_Duel.py depuis main.py (from app.pages import ...). Il ne faut jamais importer les fichiers de pages/ dans main.py : c’est Streamlit qui se charge automatiquement de les exécuter lorsque l’utilisateur clique dessus dans le menu latéral (ou via un lien st.page_link).

2. Prérequis Technique : Extraction des Sprites dans src/pyarena/io/

Où se trouve le sprite dans les fichiers JSON déjà en cache ?

def get_sprite_url(self, identifier: int | str) -> str | None:
    """Retourne l'URL du sprite officiel d'un Pokémon depuis le cache local."""
    payload = self.fetch_pokemon(identifier)
    sprites = payload.get("sprites") or {}
    return sprites.get("front_default")
